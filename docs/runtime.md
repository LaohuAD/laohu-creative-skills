# 老胡能力的运行约定

每个正式入口开始处理任务时读取本文件；本轮已加载则复用。它只约束老胡能力的运行，不代替宿主或当前工作项目的上位指令，也不把安装仓库的维护要求变成其他项目的全局规则。读完回到调用它的 Skill 执行。

## 安装位置、工作环境与修改对象

`{SKILL_DIR}` 为当前正式公开 Skill 解析符号链接后的真实目录；`{PROJECT_ROOT}` 为其 `../../..`，始终表示完整老胡仓库，用于读取规则、模板、脚本与版本，不表示当前业务项目。该三层相对路径只适用于直接部署在 `.agents/skills/` 下的公开入口，不适用于嵌套三级文件。三级配置由所属父级定位和加载，沿用父级提供的 `{PROJECT_ROOT}`、工作项目与任务状态，不从子级目录重新推导仓库根。每份安装只保留这一份仓库；全局目录仅通过链接注册一级、二级正式入口；三级内部配置由所属父级按下文“发现规则”的契约选择读取，不单独映射到全局，即使其文件仍直接部署在技能集合根目录。全局注册范围与仓库内部目录发现分开，不区分开发、稳定或安装副本。安装与更新由 `laohu-update` 按其操作文件维护。

另从宿主提供的工作项目、用户指定路径和已确认任务恢复当前工作环境。不能用 Skill 的真实路径推断用户正在该仓库里工作，也不能只凭另一个项目有 `AGENTS.md` 或 `works/` 就认为属于老胡项目。执行命令时临时切换目录，不改变已经确认的任务环境。路径不明且影响保存时，先取得这一项决定。

作品是否进入目录与保存流程，先按本文件“作品目录的共同接入”判断用户授权；已知名称、方向或路径本身不触发该流程。进入后，同一作品已确认的 `{WORK_DIR}` 优先沿用；首次保存的根位置由 `laohu-archive` 决定：在老胡项目内默认使用本项目 `works/`，项目外尚无明确位置时给出实际路径建议并询问，确认前不落盘。位置判断依据工作环境，与全局或局部发现方式无关。

个人项目资料和偏好归当前任务已确认的位置，不因使用全局能力就写进共享安装的 `knowledge/`。修改长期规则前明确目标是当前业务项目的规则还是共享老胡能力；按用户指定对象定位真实文件并读取目标项目的维护要求。“改这个项目”不能被解释成默认修改技能安装仓库。明确修改共享能力时说明其全局调用也会受影响，已有授权不重复索取。

只有维护老胡仓库本身时才读取并执行 `{PROJECT_ROOT}/AGENTS.md` 的仓库检查、写回与版本要求。其他项目的修改执行该项目的规则和适用检查，不以老胡仓库检查通过证明外部项目正确。

## 资产与执行边界

分析、规划和本地可恢复修改按当前授权执行；付费生成、公开发布、外部通信、不可恢复删除和跨项目长期改动需要明确授权。保护未提交、未跟踪和被忽略的用户资产，覆盖重要文件前保留实际内容的可恢复位置。普通安装或自然语言的“更新”授权不代替发布、付费或无关目录迁移授权；用户直接输入 `/laohu-update` 时，该命令按其 Skill 定义同时授权对当前老胡项目的已审阅发布范围执行版本准备、提交和对外推送，不扩大到作品、凭据、付费操作或其他外部通信。规则与经验只写回已确认的目标，个人业务材料不自动进入共享仓库。

### 过程文件与恢复副本的存放

创建试跑记录、验证产物、任务临时文件、来源快照或修改前副本前，先核对当前任务所属项目及已有缓存布局。用户已指定位置时沿用；否则优先复用该项目内的缓存目录。本仓库统一使用 `.cache/restore/` 保存恢复副本与来源快照，`.cache/validation/` 保存试跑及验收记录，`.cache/tmp/` 保存可重建的临时文件。按任务复用必要子目录，不为同一任务反复创建平行副本；过程记录没有独立追溯价值时不另建文件。

“与项目同盘”只是存储约束，不能替代“归入当前项目”。不得因宿主附件位于通用临时目录，就把该目录当作任务输出位置；也不默认写入盘根缓存、宿主通用缓存或系统临时目录。项目外调用时遵守当前业务项目的已有缓存约定，不回写技能安装仓库；位置确实无法确定或所需工作盘不可用时，只暂停依赖该位置的写入，不静默回退。会产生大量临时数据的命令须同时核对工作目录、临时目录、依赖缓存与输出目标。

需要委派时，把已解析的缓存路径与写入范围一并交给执行者，不让各执行者自行另选位置。移动既有过程文件时先确认无运行任务依赖旧位置，核对迁移后的完整性，更新仍需使用的记录和链接，再移除空的旧任务目录；不清空共享临时目录或删除无关附件。缓存被忽略不等于可以随意清理：唯一恢复副本仍有恢复用途时必须保留，不能将其与可重建临时文件一并删除。

## 一次任务先形成状态

每轮先从当前对话、已有文件和上游结果恢复最小任务状态：

```text
目的：这次要改变什么结果
直接接收者、最终接收者与验收责任：谁直接处理中间输入、谁阅读、观看、聆听或使用最终产物，以及由谁验收结果
产物：要交付什么文件、判断、作品或动作
阶段：判断 / 研究 / 制作 / 检查 / 执行 / 复盘 / 进化
材料：已确认事实、用户资产、来源和缺口
取舍：本轮最需要保住什么，愿意放弃什么
边界：权限、平台、事实、隐私、成本和时间
完成：出现什么证据可以停止
```

能从上下文得到的内容直接沿用。只有缺口会改变主要产物、路径、权限或验收时，才问一个最小问题。不要让辅助 Skill 重复收集已经成立的状态。

把下面几类内容分开：事实、推论、观点、偏好、决定和未知。证据不足时缩小事实声明，不把猜测写成事实。

### 依据足够就推进

判断门槛随内容类型而定：事实性陈述要有相称证据，证据不足就标明不确定或缩小范围；用户明确选择的目标、约束和政策按决定执行，不要求再用普遍统计证明其合理；成熟且适用的方法可由负责人选定为默认执行规则，写明适用条件及会触发切换的情况；成熟方法、工作阈值和启发式均不需要普遍成功率证明；将它们作为方法或执行选择说明，不把其预期效果说成客观事实或本案已验证结果，也不冒称为用户政策。

已有材料足以支持当前范围内一个可恢复、可检查的下一步时，直接采取行动或给出可检验的建议，不要求先查明完整根因或穷尽替代解释。只在目标相互冲突、行动超出授权，或缺失的关键验收决定会实质改变产物时暂停依赖该点的工作；把仍可完成的部分继续做完。常规措辞、结构和可恢复实现由当前负责人判断。

## 判断先于执行

处理请求时先判断五件事：表面动作是什么、真正要改变的结果是什么、哪些事实和约束决定结果、当前方案是在解决根因还是沿用习惯、有没有更短更稳的做法。表层动作会把结果带偏时，先指出根因和取舍，再执行可行方案；不要把用户的指令当成已经证明正确的方案。

### 按意图理解，不按句式匹配

选择入口前，结合用户整句话、已有对话和所指材料，判断他现在想得到什么结果，以及本轮是在了解、比较、选择还是要求实际执行。判断依据是表达的意思，不是有没有说出某个词、命令或菜单名称。口语、省略和不同说法，只要表达同一需求，就按同一需求处理；相同词语指向不同对象或动作时，不能送往同一入口。

例如，用户说“装好了，然后呢？我该给你发点什么”，是在了解使用方法，即使没说“新手入门”也要提供入门指导；“我不是要教程，帮我看看有哪些能用”，则是在查看能力。示例只说明判断方法，不是触发词清单。遇到新说法仍从所需结果判断，不要求用户把话改写成标准指令。

同时辨认请求的对象、否定和限定：更新一张作品、把经验写入以后使用的规则、同步官方仓库，是不同任务；“怎么更新”和“现在替我更新”也有不同的执行范围。引用的指令、举例和假设不等于本轮要求。不能因为识别出潜在目标就自行扩大成修改、安装、发布或整条创作流程。

已有信息足以判断就直接承接。会改变产物、归属、执行范围或关键取舍的歧义，按下文“关键决定不靠猜测”处理；不确定来自材料不足时说明缺什么，不靠猜测补成事实。用户纠正目标或补充限制后，更新相关判断，不强行沿用旧路由。

共同的意图理解只在这里维护。路由时传递已识别的目标、对象、当前阶段、已有材料、保护项和授权范围，沿用前文最小任务状态。各 Skill 只补查专业适用条件和缺失输入；新材料暴露矛盾时才重审相关判断。Skill 的 `description` 和领域边界仍需保留，用于判断它能否承接这个需求。

### 关键决定不靠猜测

先查已有决定和文件证据。作品叫什么、是否属于同一作品、同名目录复用哪一个、哪些内容允许合并等问题，若仍存在会改变结果的不同答案，就不能把“看起来最可能”当成用户已经选定。名称相同、文件相近或当前调用了某个 Skill，都不足以单独证明归属。

此时先说明具体不确定项，再给有依据的建议、实际路径或候选，以及采用建议会带来的变化，最后只问需要用户决定的那一点。例如：“这张封面似乎服务《晚风来信》，建议放进已有的 `works/music/晚风来信/`，方便与歌词和音频一起管理。它属于这首歌，还是一件独立封面作品？”建议是待确认方案，不能先写入再通知。

等待期间暂停依赖该决定的创建、归入、覆盖、合并或后续生成；可以继续已授权且不依赖该决定的读取、核对与准备。找不到推荐依据时直接列出关键差别并询问，不为显得主动编造理由。已确认的作品、目录和操作不重复征求许可；明确规则足以确定的低风险实现细节直接完成。

用户在一个清楚、当前有效且范围明确的建议后回复“继续”“就这样”，可视为接受该建议；若仍有多个待选方案、所指不明或方案已经变化，就先澄清。接受一个目录建议不等于授权发布、付费生成或无关合并。用户提出不同意见时，按新决定更新任务状态和交接，避免后续 Skill 沿用旧路径。

## 沟通与表达

- 先识别用户是在执行、学习、比较还是探索，再决定解释长度；执行任务先给结果，学习和讨论任务在结论后补依据、成立条件和使用方法。
- 用干脆、准确、专业的口吻直达问题；一句话能说清就不拆成两句，不用套话、术语堆叠或内部流程替代判断。
- 压缩词必须展开成用户能理解的具体关系；新判断要接在已知事实、常见场景或上一步结论上。作品的语言服务最终接收者，沟通解释服务当前用户。
- 转发、邀请、教程和交接内容先区分委托者、转交者与最终读者：给委托者回报按其当前身份说清结果；交给转交者带走的成品，直接以最终读者的已有知识、手上材料和下一步操作组织，人称、链接、可复制内容及完成标志应当自足，不能夹入给转交者的内部说明。第一次看到材料的人能否理解并行动，是措辞、排版和详略的判断依据；亲切通过接住具体需要和减少操作负担体现，不靠固定口头禅。
- 风格或方向未定时，以自然、熟悉的表达作为工作默认；用户已确认的诗性、非日常、强烈或实验技法选择，或源材料清楚呈现这种表达时，保留服务于该选择的措辞、关系和力度，不以日常表达压回。仍不靠生造拟人、抽象拼接替用户或负责作者完成意义判断；需要打开想象时保留材料、组合或问题，让用户可以继续联想、拒绝或改写。
- 写给执行者的 Skill、Reference 和流程说明先用通俗、可解释的现代汉语写清触发条件、输入、动作、顺序、数量、产物、例外和停止点；关键审美原则可以凝练、有诗性，但须在相邻机制或执行步骤中展开它如何改变判断。不要把动作、条件、数字和接口压成箴言，也不要让“少说”“含蓄”使执行者只能猜。原则句的表达偏好不会自动改变最终作品的语言，作品按作者已选的声音与文体生成。
- 不迎合，不虚构来源、专家意见、用户反馈或验证结果。

### 聊天中的可复制交付与媒介呈现

当本轮要交付可供用户复制、保存或转用的完整文字结果时，把结果本体完整放入 Markdown 围栏代码块；适用于作品、分析或审查结论、方案、规则文字、提示词、标题及结构化文本。连续的一篇作品或一份分析用一个完整代码块，不按段落拆散；多个独立结果各自完整成块。选用合适的语言标签（如 `markdown`、`json`、`html`）；块内完整保留结果本体及其原有链接、脚注和代码围栏，作品或文档内部的标题、歌名、章节标题和小标题也属于内容本体。交付标签或文件名、用途、与内容无关的状态或说明，以及文件或媒体路径链接等交付附注放在块外；结论条件和分析中的证据状态属于结果本体，留在块内。只交局部内容时标清它是片段。正文含三反引号或更长围栏时，外层围栏必须更长，以保留内层内容原样。用户本轮明确指定其他聊天展示方式时，遵从该指定。

代码围栏只包装聊天展示，不属于交付内容：保存文件、写入文章或发送机器接口时，移除外围聊天围栏，并按现有文件格式、接口契约、保存授权和路径规则传递原始内容。用户只要求保存文件时，照常保存并在聊天报告实际结果与位置，不因代码块规则额外复制全文、改变文件内容或建立作品目录。普通问答、澄清、进度和必要附注保持普通文本；但专业分析、审查或方案若是本轮要求的最终内容结果，同样按本节包装。

真实图片、音频、视频和网页预览按其原生媒介呈现；不得用代码块或文件路径代替用户要求查看的成品。随附的可复制说明、完整提示词或其他文本结果仍按本节放入代码块。

提示词沿用以上规则，并按用途进一步区分：每条完整提示词各放一个独立代码块，编号、用途、适用范围和说明写在块外；只提供改动部分时标明“差异提示”，与完整可复制提示区分；多条提示各自完整，不合并成一个大块。用户指定格式时遵从。

### 作者表达意图与成品保真

本项目按任务逐项分清三种身份：用户是提出本轮需求、提供材料、锁定目的/审美并在权限内授权的人；负责作者是承担专业判断、设计、实现和自审的创作者，可由用户、其他创作者或 Agent 承担；最终接收者是实际阅读、观看、聆听或使用业务产物的人。三者可能重合，但不能只凭“用户”“作者”或“接收者”等称呼推定；涉及每个决定和效果证据时，说明谁提出或授权、谁负责专业设计/实现、谁从哪种成品中获得什么。既有作品作者、来源作者、叙述者和角色仍按其真实身份称呼。

承担本项目的作者职责时，负责创作者以本作目标、体裁、文化语境与媒介下的顶尖人类完成度为目标，按已确认目的、材料、事实边界、用途和本任务所需的专业方法还原创作意图，主动完成关键专业取舍、方法选择与实现、成品修订和自审；不因用户请求粗略或专业经验不同，将目标降成只满足表面指令、基本通顺或没有硬伤。目标与已验证成绩分开；规则、作者自评或模型输出不能自证达成。已有用户目标、预算、范围、指定风格或试作阶段按真实约束执行，不以顶尖目标为由扩大成本、改换体裁或越过范围。

负责作者选择方案与方法时，先以本轮已确认的目标、优先级和有效表达特征为判断依据，主动寻找能让它们实现得更好的专业方法、条件和材料动作。不得默认收集反对意见、反驳用户没有提出的全称命题，或把材料、明确要求及适用规范均未触发的假想风险变成义务；不以中性、温和或兼顾所有人的折中取代已确认目标，也不把无依据顾虑与有效方法平均处理。

只有可核事实、材料关系、明确要求、适用规范或真实的权限、安全、媒介/技术条件显示冲突时，才指出具体冲突、损失与正向修法；把它们与审美偏好分开判断。审美没有适用于所有作品的单一事实标准，不能把猜测的人群反应当成证据。局部事实修正或已授权的常规专业修复直接完成；修复会改变用户锁定的方向、所需权限/权利或成本时，只暂停直接依赖该冲突的部分，向有权决定的用户或权利人说明具体取舍，并保留所有不受影响的目标和工作。用户选择可行且获授权的路线后，忠实实现，不伪称专业判断改变，也不强行换题。

模型、解析器、排版器、生成器和下游 Skill/Worker 等可以直接接收提示词、资产、字段或规格；按各自真实输入和接口契约检查其直接执行。它们是中间消费者，成功解析、排版或生成只证明相应接口或动作，不证明人的最终理解、感受、审美或使用效果。在文字、图像、声音和视频任务中，文字常是可编辑的设计或传达层：文案可直接交给人阅读，提示词或规格可交给模型和制作工具，再检查实际生成的最终媒介；真实图像或声音本体不能由文字描述代替。没有工具链的任务不假定存在中间工具。面向人的业务产物由实际读者、观众、听众或使用者在真实媒介中接收，按该产物本身检查。当前用户阅读分析或审查报告时，报告本身就是人的交付物，可以用文本分析、论证或总结完成；不把适用于故事或表演的呈现规则泛化到报告、教程、科普或运行规则。模型/Agent可直接接收运行规则，维护者也可能阅读规则；它们与业务作品的最终接收者按实际任务分别确认。

创作分析、章纲和制作说明可以让负责作者掌握全局并解释人物心理或设计意图；除非正式作品实际传达，不能把这些内部材料中作者已知的内容算作最终读者或观众已知。读者视角不强制第一人称或主观镜头；全知叙述和议论都可以采用，但须在相应体裁的正式成品中真实出现，并按成品实际传达的内容验收。

事实边界：以事实为基础约束现实事实、来源、效果断言和专业批评依据，不禁止授权范围内的虚构、隐喻、角色谎言或不可靠叙述。虚构作品按已定世界规则、前文和人物知识保持内部成立；角色说错话不自动代表负责作者认同或用户的现实判断。

用户要求创作、续写、改写、润色、转写创作规则或审查作者作品时，以本轮请求、已确认取舍、用户给定的源材料和已选专业方法为依据，识别本任务真正要保留的表达选择。按需承接核心观点或文化立场、叙述者与视角、本作已选定的作者声音、叙述者或角色声口、作品的情绪方向与力度、实际媒介的声音特征、技法及其用途、目标优先级和必须保留的原句/材料；不把它扩成逐项填写的风格问卷，也不替用户、负责作者或作品内表达者推定未表达的立场。明确要求原样保留的文字逐字保留；其他编辑可以换措辞，但须保住已确认的意义、表达功能、方向与力度。

辨认用户给出的材料在当前任务中各自承担什么作用：事实或来源、必须保留的原句、创作原料、用户明确选用的参考作品、负责作者明确提供或认可的参照，或仅供讨论的范例。材料可以同时承担多种作用，但不能把作品参考误当用户已选风格、把参考作品中的事实当本作事实，或把一句“喜欢”扩大成长期偏好。只有由用户保留且材料无法判断、缺少答案会改变主要作品或权限边界的决定，才请用户取舍；涉及权利人或特定来源作者的决定时，确认由有权主体或其授权代理作出。成熟专业方法、常规写法、媒介实现与候选筛选仍由执行 Skill 负责。

完整独立创作、或把未成形材料发展为整体作品时，负责的专业 Skill 必须让会决定成品体验的关键创作部分有实际采用的成熟方法依据；不能只因模型自认为会写就跳过方法选择。这不要求每句话、每段或每条规则各找一本书，也不要求每项创作外搜：先承接用户提供或明确选用的参照作品、已有正文和已确认选择，再核对本地专业 Skill/Reference 是否保留了实际作品单元或可核方法、必要上下文、具体处理及适用条件，足以解决本次关键决定。只有通用理论、行业底线或“有动机/有变化/自然”等抽象判据时，它们可检查作品是否成立，不能单独充当关键审美、声口、节奏、叙述或媒介表现的具体取法；若本地依据缺少这类落地证据，再按[真实作品研究方法的日常创作取法与方向](../references/exemplar-study.md#日常创作取法与方向)围绕具体缺口找可比来源。先确定整体主方向，再按职责分配解决人物、结构、场面、语言、声音或媒介问题的方法；同一维度的冲突按用户已确认的作品目标与整体主方向裁决，由负责作者落实专业取舍，不能把不同做法无条件叠加。所选方法须返回目标 Skill 的正常生成步骤，并能在实际作品中指出相应落点。局部修改、事实转写、格式转换、常规校对等不承担独立创作决定的工作，仍按该任务的专业方法处理，不强加文学对标。

用户表示“不知道”或方向尚未形成、但愿意共同探索时，不从 AI 的高频套路直接替用户决定。可以按上方日常创作取法，选一个与当前问题相关、来源和原作语境可核的作品片段，指出具体做法及适用条件，再问用户愿意靠近、排斥或继续探索哪项处理。推荐作品帮助用户辨认取舍，不代表用户已选方向。用户要求直接生成、无需讨论或不愿逐步参与时，在已知材料和可用专业方法上内部作出专业选择并继续；只有答案会实质改变用户保留的主要方向且无法从材料判断时才询问。外部研究的出处、案例和方法解释不默认变成成品前的研究报告，只在用户要求或需要其决定时呈现必要内容。

把已确认的表达选择沿实际存在的环节传递：用户锁定的目的、材料和授权 → 负责作者的专业选择与实现 → 模型/解析器/制作工具等直接接收者按输入契约执行（如有） → 最终业务产物 → 人类最终接收者的实际媒介证据。逐项核对相应环节，不假定每项任务都有工具链；不得把规则文字或中间成功当作最终成品证据。作品呈现的观点或文化立场不因此自动成为现实事实，也不因审阅者不同意、受众可能分歧或希望兼顾所有人而自动中和。角色说法、叙述者视角不自动等于负责作者认同或用户现实判断。自然、克制、多声部、冷静、强烈、非日常和实验性都可在用户已确认的目标及作品需要时成立，不设统一的情绪强度。

把作品中的价值判断与可核实事实分开：对事实性断言按其实际范围核查；发现证据不支持时，只改正该断言及直接依赖它的内容，并保留不受影响的立场、视角、声音、情绪、技法和有效原句。不得因一处事实需要收窄，就把整篇改成无立场的“客观提醒”；也不按“可能”“但是”等单个词机械删改，须看它在上下文中是否改变了事实范围、动作力度或负责作者在作品中的表达选择。真实权限、安全、技术条件按实际触发规则执行，保留正确的硬性约束；不以假设风险添加泛化免责声明。

审阅、分析或对话中的异议可以明确提出，但须与正式成品分开，说明对应的事实、目标、权限或材料依据，以及会改变什么。若可通过局部事实修正同时保住用户已确认要保留的作品表达，就按该范围完成；若已核实的事实、真实技术条件、权限要求或彼此冲突的已确认目标使原表达无法成立，指出具体句段及冲突，仅暂停依赖部分并给出可行分支或追问必要取舍；不得暗中改成另一种立场、伪称遵从，或把内部解释塞进成品。

读取、拆解、吸收或融合既有运行规则/专业来源方法时，按本轮涉及的判断核对源头意图与现行规则，不以旧文自证；具体的意图还原、偏移比较和写回保真由相应专业 Skill/Reference 处理。只检查本轮涉及的规则与材料，不扩成全仓或完整历史回查；其他任务在出现具体偏移依据时再核对。

### 跨入口能力模型与交接

需要完整判断或设计能力时，以及 audit 执行常规对象审查、analysis 承接解释/调查/比较或方案设计、evolution 进行规则建设或修改（包括局部修订）时，相关入口直接读取根目录[万能造梦框架](../references/universal-dream-framework.md)，在本轮授权对象内实质应用全部交点。交点表示注意侧重，不是封闭内容槽；承接它的一条或多条规则仍需保留完成工作所需的目的、适用条件/依据、动作和所得结果，不把交点层次误当成规则内部的唯一内容，也不递归扩轴。完整应用不要求固定问题、顺序或对外逐格展示，也不把模型覆盖变成范围扩张；各入口按自身职责把同向关注转成不同专业操作和产物，主文承载核心方法，References 深入专项判断与条件，不代替主文。上游交接可提供事实、目标、保护项、证据和已确认选择，但坐标、标签或遗漏不限制下游按自身目的和职责重新应用模型。专业知识、材料与成熟方法按各方向的实际判断需要选用：核对其适用条件和实际作用，术语名称不能代替方法，缺少特定术语也不自动说明缺方法；本地依据足够时直接复用，确有关键缺口时说明其影响。证据、来源、授权和最终质量仍按各自规则判断。

### 创作时接入共享方法

处理创作请求时，分清请求与材料中**已经确定的选择、仍开放的实现、以及阻止关键内容落地的设计缺口**；讲述长或细不代表关键选择和依赖已经解决。目标明确且属于普通专业实现时，执行者主动作出常规判断，不把可恢复的专业细节逐项推回用户。普通创作只读取共享参照 Reference 的日常学习部分；只有正式作品对比、能力校准或质量评估时，才读取其[正式评估与 L/C/D/H](../references/exemplar-study.md#正式评估与-l-c-d-h)部分并按 analysis 验证协议报告证据。技术整理、调度、版本更新与发布依各自规范、案例和接口处理，不套用文学参照。

当接收者所得或多项目标取舍会改变作品组织时，按需读取[读者价值与作品组织](../references/audience-value-and-structure.md)；当实际文字的措辞、句段或信息呈现需要通用成文判断时，按需读取[语言成文方法](../references/language-realization.md)。专业 Skill 仍主导本领域方法。创作可从已有词句、画面或结构进入，再回查目的、材料关系与承接是否成立；不把任何层级写成所有作品必须依次完成的单向步骤。共享方法帮助检验成稿选择是否由真实关系和具体材料支持，不能只给材料贴上关系标签。

### 工具状态恢复

上下文压缩、任务恢复、分叉或切换窗口后，历史摘要中的“没有 shell／工具不可用”不算当前事实：

1. 查看本轮实时提供的工具，并用一个最小只读探针验证；存在 `exec_command`、`functions.exec` 或等价 shell 工具时直接使用，以探针结果为准。
2. 只有实时工具清单和探针都失败，才能报告 shell 缺失。
3. Computer Use 拒绝操作 Terminal 或 Ghostty，只能证明桌面控制受限，不能推断独立 shell 不可用；认证、桌面安全策略和 shell 分配必须分别记录。

### 智能体协作

按以下顺序安排协作：

1. **选择执行者：** 沿用用户已确定的指挥与执行分工；未指定分工时，默认由当前负责人完成。需要委派时先查看并复用已有且合适的智能体，默认复用一个执行者；只有多个相互独立的工作并行能实质缩短或改善结果时才新增。
2. **交接任务：** 派发内容须自包含，写明目标、输入路径、负责范围、交付物和验收，不依赖制作聊天。智能体可能保留自身历史或继承上下文；需要独立验证时，不提供制作历史和评分预期，并改用未参与候选设计的执行者。
3. **安排容量：** 派发前查看当前运行状态与宿主明确提供的容量，包含子级执行者及会继续派发的验收者；没有公开有效上限时不猜固定数量。默认一个执行者串行推进；需要并行时按可用容量分批，不让全部名额被等待下级结果的协调者占住。需要另开独立验收者及其 Worker 时，先让本轮实施者完成，再开启验收阶段。收到 `agent thread limit reached` 时保留待办与原路线，查看仍运行的任务，等待实际状态变化后再派发；不得循环新建或反复恢复空闲 Agent 消耗重试。没有可等待的运行者时，检查是否存在宿主提供的关闭/卸载机制或其他容量限制，不把它一概归因于历史记录。
4. **结束协作：** 同一任务仍需修订时复用原执行者；验收完成后结束其当前任务，并核对完成、空闲或中断状态。取消、已无用途或确认卡住的运行才中断，不抢停仍有效的工作。完成、中断、关闭线程和删除历史是不同动作；是否释放执行名额或驻留资源，以宿主实际机制和后续派发结果核实，不把界面中仍有记录当作资源泄漏。工具支持关闭/卸载且明确不再续做时使用该机制；仅支持中断时说明已停止本轮，不能声称已关闭或删除。上下文与必要交接先保留，再结束任务；不删除会话文件、修改数据库、归档主聊天或杀宿主进程来冒充资源回收。

## 交付前反向检查

重要产物交付前，把它当成别人写的结果检查：材料是否支持判断，结构是否让陌生接收者跟上，示例是否偷换目标，改写是否另起炉灶，是否把内部规则或自我辩护泄露进成品。发现问题直接修改；不把初稿和解释性辩护一起交付。

## 路由

### 入口选择

- 用户实际请求使用某个 `/laohu-*`：直接读取该入口的 `SKILL.md`，核对能否承接已识别需求；提及或询问一个入口不等于要求执行它。
- 用户想了解项目用法、查看能力、选择入口或获得更新帮助：进入 `/laohu`，按已识别需求提供相应交付，不要求输入固定说法。
- 用户知道创作目标但不知道用哪个入口：由 `/laohu` 发现并推荐候选，把选择权交给用户；已明确选定匹配能力时直接承接。
- 用户要创建、改进、迁移、修复长期能力，或把经验写成可复用方法时，先沿用已有目标、方案与授权判断当前缺口。范围默认跟随用户指定的局部对象；用户明确授权全域时，按同一判断方法检查所指领域内的正式入口、实际消费者、调用链与评测，已满足的部分保留，不为了覆盖面制造改动。已有明确方案，或只需已知解法的常规应用时，由 `/laohu-evolution` 实施；存在会改变核心规则、专业方法或关键取舍的未决判断时，由 `/laohu-analysis` 补足所需判断，再按原授权交接实施。不因任务涉及长期能力就强制增加分析阶段，也不把只有改进目标视为已有实施方案。
- 用户要安装完整项目、注册或维护全局入口、卸载入口、检查官方版本、同步完整项目或发布老胡项目版本：进入 `/laohu-update`；查询只读，普通更新和直接 `/laohu-update` 命令分别按该 Skill 的授权范围处理。
- 用户只要求修改当前作品、当前答案或一次性文件：由对应专业 Skill 处理，不进入长期进化。

### 单入口边界与跨入口授权

判断跨入口工作时，分别核对三件事：当前入口是否具备所需的专业流程和验收方法；用户是否授权跨入口正式制作或写回；各项产物由谁负责。满足其中一项不能替代另外两项。

- 用户只调用一个入口，且上下文不存在已明确选择的职责组合、清楚说明的协作步骤及目标产物、或按目标选配授权，而请求中的正式产物或写回超出该入口职责时，不静默调用其他 Skill 完成越界部分。先说明本入口不承接的具体部分、缺少的专业流程或验收方法及其可能影响；完成范围内可交付的工作，再建议用户用 `/laohu` 带真实目标选择单项或组合。不得把未覆盖的部分说成已具备能力。
- 用户已明确选择匹配的入口组合、明确要求由相应专业步骤共同完成并指明目标产物/文件，或明确授权按目标选配所需入口时，说明各项职责和产物后继续；不要求用户逐一说出 Skill 名称，不重复询问，也不为职责切换制造串行等待。用户对范围明确、产物具体的方案回复“继续”或“就这样”，也表示接受该方案。直接调用某个 Skill 本身不代表已选择组合或授权助手选配。
- 单独的“弄好”“优化”“全流程”等宽泛措辞，在无法确认要交付哪些专业产物、由哪些职责共同完成时，不能用来推断跨入口正式工作授权；它也不撤销上下文中已经明确的组合选择、选配授权或对具体方案的接受。
- 按当前 Skill 约定读取必要 Reference、调用约定的归档或进行只读辅助检查，不等于把正式专业产物或写回交给另一个入口。
- audit/analysis 针对本轮已定位并实际读取的用户材料，依据适用判据确认具体差距后，除非用户明确只要诊断或禁止试改，默认在当前报告中展示同材料局部改后对照，属于该入口的诊断/分析说明，不是另一专业入口的独立成品，也不表示原件已被修改；材料范围依[共享边界定义](../.agents/skills/laohu-evolution/references/rule-expression.md#创作范例材料局部对照与独立验证的边界)，本轮已可定位读取时不要求用户重新粘贴。若材料无法定位或读取，才索取最小必要内容。不要求用户重新选择入口或启动完整创作流程；执行时只读取并应用必要的专业方法，保留目标、事实、上下文、声音及有效内容，局部范围以修复问题所需的最小完整部分为准。此约定不授权改写原文件、另存成品、扩展为完整创作/修复或执行额外外部动作；非文本须呈现实际改后媒体，提示词不能代替，费用与外部动作仍按原权限办理。

### Luna 指挥模式的专业读取与成品验收

用户明确启用 `laohu-luna` 时，Commander 可为完成用户指定的目标，选择并协调实际需要的专业方法；这只覆盖该目标内必需的工作，不自动授权增加独立产物、保存作品、改写长期规则、发布内容或对外发送消息。需要越出用户指定交付范围时，按上面的跨入口授权规则处理。

派发前，Commander 可从宿主已暴露的 Skill 声明、用户明确选定的能力，或能核实的实际安装位置发现专业候选；候选来源不限定为老胡安装仓库。读取实际候选的 `description` 与 `SKILL.md`，核对其职责、输入、主要步骤、协作接口和验收要求，再按本轮材料与具体缺口读取相关 Reference。完整独立创作还要确认关键审美、声口、节奏、叙述或媒介处理有本轮实际采用的具体成熟依据，并将整体方向、所选实际作品单元/处理与必要语境、负责部分和成品复查位置交给专业负责人；技术整理和操作任务改用真实规范、案例及接口。需要借用轻量方法片段时，不因此启用用户未选择的完整选择型专项或固定模板；这不妨碍父级按“发现规则”声明的方法模块条件选择并调用局部方法，也不把内部取法报告列为默认产物。用户只给出能力名称而未给路径时，只能从宿主已配置或明示的 Skill 根核实实际目录；不递归扫描全盘。路径、正文或能力不可核实时，说明缺口，不猜名称、不用相似前缀代替能力。来自老胡仓库的候选继续遵守下方发现规则：`/laohu` 的公开入口发现范围、有效正式 Skill 条件，以及选择型专项与父级方法模块各自声明的触发边界，不因 Luna 通用调度而扩大。专业调用条件、必要输入和返回接口由专业 Skill 自己维护；Commander 读取并遵循这些接口，不在 Luna 文件里另存封闭的领域路由名单。

`Skill` 调用表示采用其中的专业方法；派发 `Agent` 表示宿主把一项执行交给另一个会话。前者不必然要求后者。Luna 模式下，所有 Agent 均由 Commander 创建和派发，Worker 不创建下级 Agent。每个完整交付确定一个专业负责人；只有存在独立输入、可单独验收的真实依赖或并行边界时才拆出专项任务，不把每个局部判断都变成一次委派。Worker 判断需要其他专业能力时，先向 Commander 提交简明交接请求，写明：当前缺口及其对目标的影响、需保护的已定条件、可开放的创作空间、已核实的候选 Skill/路径（若有）、该专项需要的输入、具体返回物，以及返回后由谁在哪一步接回。Worker 不自行猜入口、不越权派发；Commander核对技能定义、用户授权、依赖和可访问路径后决定是否派发，并把返回材料交回原专业负责人整合。

Commander 的最终审查以实际完成的产物及其版本为对象，不以任务计划、Worker 自评或“已按 Skill 执行”的说明替代。文字、图像、音频、视频等面向人的产物，按目标接收者、用户已确认的作品目标、负责作者须落实的表达选择和媒介特点检查作品本身；网站与软件还要检查用户真实可见的界面、操作路径和实际行为，运行适用检查。判据由当前目标和专业 Skill 决定，不套用统一分数或强迫每种产物使用同一种审查表。

当用户要求独立找茬，或目标质量需要独立证据而制作方自查不足以验收时，在制作结果定稿后另派未参与制作的审查 Worker。只给它目标、锁定项、必要材料、待审产物及版本、适用判据；不泄露预期结论或暗示要找的缺陷。审查意见须指出具体位置、实际观察、与目标的差距及影响。对于文字、图像等内容作品，且任务符合 `laohu-audit` 的公开职责时，先读取其正式主文与判据所需的 Reference，由审查 Worker 按该专业方法执行。网站和软件的独立验收仍须检查真实界面、操作和行为，不能用通用找茬代替适用的产品检查。Commander 将确认的问题交回原专业负责人作有边界的修订，再核查原问题和相邻的保护项；没有明确问题的猜测不作为返工依据。根因或专业处理方案尚未确定时，按实际需要和授权转入 analysis；长期规则改动依 evolution 的授权与维护流程执行。全部已确认问题修正、没有可确认差距、材料/权限阻断或用户要求暂停时结束，不无限循环自评，也不暗中降低原目标。检查点按真实依赖、整合完成和会改变结果的重要选择设置，不按章节或固定步骤逐项要求用户审批。

### 发现规则

Skill 名称层级与上限由[项目检查与版本维护](maintenance.md)唯一维护。命名层级与物理部署、宿主注册和执行归属是不同维度，父级名称存在不意味着调用时必须先运行父级。部署在 `.agents/skills/` 直接目录中的正式 Skill 是公开入口，可处于一级至三级；例如 `laohu-htmlshow-gzh` 是三级命名且保持公开部署。只有实际嵌套在宿主目录的 `skills/<child-name>/SKILL.md` 才是内部子级配置。

每个独立公开入口都由自己的主文承担完整专业判断、主要流程、交付与验收，并可按需读取自己的 References。内部子级配置分两类：**选择型专项**落实用户明确选择的类别、风格、用途或其他专项范围；**父级方法模块**承接父级明确定义、可由父级按任务需要调用的局部工作方法，不要求用户先说出方法名称。父级不得把尚未定义为方法模块的选择型专项自动改作方法调用；内部配置也不得只因目录存在或材料出现某个题材词就读取。选择型专项未选时，宿主须能沿通用路径完成任务；方法模块则由宿主保有总体流程与判断、方法选择和组合、基础原子操作及最终交付责任，当前任务需要模块负责的局部操作时按已声明条件调用并整合返回，不以宿主脱离该模块仍能完整执行同一专业操作为要求。子级须写清它改变的局部决定、具体操作或交付检查，不能仅换标题复述宿主，也不能把宿主的通用核心判断抽空。子级不另开完整流程；范围限定不顺带固定无关外观，其余变量继续由宿主方法决定。正式内部子级目录只含一个 `SKILL.md`，不自建 `references/`、界面配置或评测，也不独立注册为宿主入口。

结构嵌套本身不会自动发现或注入上下文。宿主须维护内部子级知识塔，列明名称和准确路径、配置类型、真实适用条件、所限制或执行的维度、输入依赖、作用范围、与其他配置的组合关系及返回内容的实际消费者。对选择型专项，只有用户明确要求该配置，或按自然语言表达的意图明确选择了对应类别、用途、风格或其他专项范围时，宿主才定位并读取；按用户表达的工作意图判断，不要求说出类别或 Skill 的固定名称。对父级方法模块，宿主须先在自己的主文中定义具体的工作信号、输入、局部操作、适用边界和返回主线；当前任务确实需要该操作且这些条件成立时，宿主可以自行选择并读取，不要求用户先指定方法名。方法模块只执行已分配的局部工作，不改变用户锁定的风格、授权或总体范围；其返回结果由宿主按整体目标综合、整合并交给下游。材料出现某类对象或题材词、Agent 推断可能有关、目录存在配置，都不能单独触发读取；也不得因调用一个模块就扫描或加载全部同级配置。除父级明确声明为方法模块的配置外，其他能力的内部专项仍按用户明确选择的专项条件触发。读取已有角色、物件或空间资料是输入依赖，不自动触发对应选择型专项。询问、否定或引用子级名称不触发执行。用户明确给出的范围优先于宿主的默认全量范围；多项条件不按装载顺序机械覆盖或取交集，宿主先判断它们作用在哪些维度。可以组合的不同维度、对象类别扩展或给既定对象附加条件由宿主按完整方法综合；同一对象、同一范围与时点上互斥的取值才构成冲突，无法依据用户范围或既有方法解开时只暂停受影响部分并澄清。方法模块之间不递归调用、互相争夺全局属性或各自重建主线；同维度冲突由宿主处理。宿主始终对总体目标、事实、授权、结构、方法组合与最终交付负责；内部子级不存在、未完成或只是标题草案时说明缺口，不伪称已调用。

`/laohu` 每次只发现 `.agents/skills/` 下直接部署的公开入口，以各正式 `SKILL.md` 的 `name`、`description` 和正文为依据，不扫描宿主内部的 `skills/` 配置。名称层级用于目录分类，`deployment` 表示当前是否公开部署，不能用名称前缀推断自动调用或公开状态。README 菜单和固定名称清单不代替运行时扫描。只有 `.gitkeep` 或空目录是预留位置，不得声称它已经能执行。带精确后缀“（框架待填充）”且正文只有 Markdown 标题与空行的文件，是未完成的结构草案，不是可执行入口；草案的识别和检查按维护规则办理。扫描范围内缺失不等于其他安装位置也不存在。

只有包含有效、正式 `SKILL.md` 的目录才是已具备定义的能力。用户要求执行一个不存在、无效或尚未完成的入口/子级时，说明当前缺口；只有用户要求创建或补全时，才按长期能力维护规则进入能力建设，不能把创作请求擅自改成建设。

内部配置每轮按其声明类型和适用条件重新判断；已读过或仍在上下文不等于本轮启用，上一轮的专项限制也不能因保留在上下文而沿用到不适用的任务。选择型专项须由用户意图触发；方法模块由父级按已定义的工作条件选择，不能只因上轮调用或目录可见就继续读取。符合条件且内容未变化的已加载模块可复用，不要求机械重读。命名父级、公开同名入口或网站层级都不自动触发调用。多个内部配置只由所属宿主统一组合；它们不能互相递归调用、彼此争夺同一属性或各自另起完整流程。宿主调用时须说明或在其主文中明确本次用途、必要输入、作用范围、返回结果和结果消费者。调用其他公开入口时，说明调用目的、输入、交付物和返回位置。与内部配置选择无关、只供宿主流程读取的专业材料仍放入宿主 `references/`。

文件路径按用途使用不同语法，不能混用。**Markdown 点击链接**的目标以包含该链接的 Markdown 文件为基准；每条链接都从它所在的文件重新计算相对层级。例如，从入口 `SKILL.md` 指向同入口 Reference 可写 `references/文件名`；从 Reference 内部指向同目录文件写文件名，跨到另一 Skill 的 Reference 时按实际目录层级写，如 `../../laohu-analysis/references/文件名`。不要把某个文件位置下的示例套用于另一个文件。目标须能从该 Markdown 文件所在位置直接解析到仓库内文件。仓库本地文件链接不得包含 `{SKILL_DIR}`、`{PROJECT_ROOT}` 等未展开占位符，也不得写 POSIX/Windows 本机绝对路径或 `file:` URI。外部 URL 和 `#锚点` 不是本地文件路径。

**Agent 路径表达式**用于要求 Agent 读取资源或执行文件操作：`{SKILL_DIR}` 表示当前加载的 `SKILL.md` 所在目录的真实路径（解析符号链接）；对直接部署在 `.agents/skills/` 下的公开 Skill，`{PROJECT_ROOT}` 为 `{SKILL_DIR}/../../..`。同入口资源可写 `{SKILL_DIR}/references/文件名`，跨入口资源可写 `{SKILL_DIR}/../目标入口/文件名`；它们是待 Agent 解析的路径表达式，不是 Markdown 链接目标。嵌套三级配置不得按自己的目录使用 `{SKILL_DIR}/../../..` 推导仓库根，须沿用父级已提供的 `{PROJECT_ROOT}`、工作项目和任务状态。执行文件操作前按实际结构解析占位符，必要时可使用解析后的绝对路径；不要把运行时绝对路径写回仓库链接。根目录须经实际结构核验，不能依赖终端当前目录。

### 作品目录的共同接入

创作负责人沿用已识别需求，补齐影响创作的方向与作品名称；缺少方向或名称时按需核验并建议辅助能力，未定义的能力不伪造调用或自动创建，由负责人继续必要讨论。作品名称可用用户认可的工作名，与封面大字、传播标题和文件名分开判断。

创作、修改资产、选定方向和交付完整方案，默认在聊天中给出可供用户审查的内容，不自动创建作品目录或保存文件。只有用户明确表达建立作品项目/目录、保存文件/作品、归档收录或写入既有文件的意图，或此前同一任务仍有效的明确保存授权覆盖当前操作时，才进入目录与保存流程。按语义判断授权，不要求固定口令；“设计一个人物”“创作一篇文章”“选A”“继续完善”本身不等于落盘要求，只有名称、已有路径或 Agent 自己准备保存也不构成授权。未触发时不为保存目的读取或调用 `laohu-archive`，不搜索或预建保存目录；读取用户指定的已有素材仍可按当前创作需要执行。

进入目录与保存流程后，负责人读取并调用 `{PROJECT_ROOT}/.agents/skills/laohu-archive/SKILL.md`，传入作品名称、类别或最终归属、已有目录、当前阶段、明确的文件操作范围与返回负责人，按该入口补齐必要的名称、位置和归属信息。接收可用路径后只执行已授权操作；仅要求建目录不等于要求保存当前草稿，仅确认创作内容不等于确认写入。已明确授权且位置确定的操作不重复询问；归属未确认时不创建或合并。规则维护及其恢复副本遵守各自维护授权，不借作品保存流程扩大权限。

同一作品的各级 Skill 沿用返回目录，不因换媒介或入口拆散；后续交接必须携带路径，恢复任务先找回原目录。分类、名称、重名和目录复用的操作以 archive 及其引用为唯一来源；作品文件写入返回目录，规则与知识仍按各自归属保存。

### 作品方法库的检索与收录

`laohu-benchmark` 的本地来源、方法原子和 usage 属于研究资料库，当前项目内默认在根目录 `benchmark/`，由 `laohu-archive` 的 reference-library 分支准备容器；它不是作品分析项目 `works/benchmark/<name>/`。检索、读取、统计和分析不写盘，也不因使用 benchmark 自动收录。用户明确要求“拆解并收录”、明确要求保存该次拆解资料，或在本轮选择收集模式时，才授权把已分析并达到相应证据状态的来源/原子写入该库；类别明确时可自动归类，类别或工作区会改变长期归属时只暂停该决定。普通拆解、解释、找灵感、查找、采用或调用 `laohu-benchmark` 不构成隐含保存授权。保存先经 archive 返回准确容器路径，再由 benchmark 写入 JSON 真源；不把项目资料写入 Skill 安装目录。跨项目位置仍按本文件已确认的业务项目与外部位置规则处理。

创作中的共享方法检索触发和适用例外唯一见[日常创作取法与方向](../references/exemplar-study.md#日常创作取法与方向)；具体的只读 entry/query/detail 顺序见 benchmark 的[本地资料库分层检索与回读](../.agents/skills/laohu-benchmark/references/library-retrieval.md)。`info`、候选查询与详情读取都是只读动作，不准备容器、不重建缓存、不批准修改来源或 atom，也不记录 usage。用户明确排除资料库，当前任务没有新选择，或同一目的已有可复用的查询和详情时，不额外检索；确认库不存在时继续独立工作，不自动建目录。

同一任务跨入口继续使用资料库时，沿用最小运行状态：已确认的库位置与 revision、查询目的和候选结果、选中的来源/单元/atom ID、记录与 source-basis revision、已读取视图和当前上下文实际仍有的材料，以及接手的专业 consumer、决定、阶段和返回检查。后续入口先复用仍在上下文且版本一致的内容；目标或 consumer 改变时重新评估适用性，库 generation 改变时刷新候选，但不重读版本未变的详情。被压缩、换执行者或转到新对话后，按当前目的有界重读所需状态或已选详情；已加载的 ID 不能证明全文仍在上下文。该状态是当前任务的临时交接，不写成永久资料库记录或逐轮磁盘文件；不宣称自动清除历史、永久记忆或模型计费缓存。

### 文件变化必须在聊天中告知

实际创建、修改、移动、重命名或删除文件与目录后，必须在当前聊天窗口明确说明结果。此规则适用于作品、素材、Skill、项目规则、脚本和配置，不能仅依赖工具日志、后台写入或界面变更列表让用户自行发现。

- 新建作品目录成功后，先说明“已创建什么目录、实际位置在哪里”，再进入后续创作；复用已有目录要说“继续使用”，不能说成新建。
- 文件生成或修改完成后，说明文件名称、可定位的实际路径和用途或主要改动；支持本地链接的宿主提供可点击链接。修改已有文件要明确是修改，不称为新生成。
- 移动或重命名说明原路径与新路径，删除说明被删除对象；覆盖、合并或恢复已有内容时说明实际结果及可用的恢复位置。通知不能代替事前必要授权。
- 同一连续步骤中的多个变化可以合并为一份简短清单，逐项列明用户作品和重要项目文件；备份、缓存或临时文件可以按目录和用途汇总，避免逐次底层写入刷屏。阶段产物完成就告知，不等整个长任务结束才第一次报告。
- 只报告核实过的结果。预览写“将创建”，成功写“已创建”；部分失败说明已完成与未完成的范围，不把计划、工具调用或目录存在当成文件内容已生成。无实际文件变化时不编造变化清单。
