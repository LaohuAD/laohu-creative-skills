# 项目检查与版本维护

## 本地检查

实施负责人在修改 Skill、Reference、项目工具、引用、目录或版本前读取本节，完成前运行结构检查；修改项目工具、发现或版本逻辑时必须同时运行离线回归。完成后返回原实施流程，报告检查结果和未验证范围。

在已核验的仓库根目录运行（Python 3.9 或更新版本，无第三方依赖）：

```bash
python3 tools/check_project.py
python3 tools/check_project.py --test
```

第一条检查结构，第二条再运行入口发现、版本维护、公众号工具、作品目录工具和全局入口管理的离线回归；不自动执行需要 Agent 生成内容的评测案例。公众号预览的 JavaScript 分支测试需要 Node.js；缺少时 unittest 明确跳过，不能据此声称复制行为已验证。可加 `--json` 获取机器可读结果；通过退出 0，失败退出 1。

**覆盖项：** 检查必需文件、正式入口的共同运行文件接入、Skill 名称与描述、每个正式入口的 Codex 名称／简短说明／默认提示词、平铺入口与动态发现一致性、Markdown 显式文件链接、JSON 格式、Python 语法、README 命令归属及版本一致性。每份 README 的能力目录表须覆盖当前正式入口；合法预留入口可以列出，也不要求全部预留项都出现在表中。

**Markdown 解析范围：** 检查器剥离围栏和行内代码后，从当前支持的内联链接与图片语法提取目标；按包含链接的文件位置解析仓库本地目标并进行 URL 解码，报告未展开的路径占位符和 POSIX、Windows 或 `file:` 本机绝对路径。它不是完整 Markdown/CommonMark 解析器；不验证远端链接可达性、锚点是否存在、代码示例路径或自然语言表达的依赖。

**评测材料检查：** 评测套件按 `prompt`、`context`（含 `conversation_context`）、`input_files` 和 `fixture_setup` 检查重复输入，不比较预期行为或评测标签。显式声明 `execution_mode: write` 的案例还检查 `fixture_setup.files` 非空、路径位于隔离目录内、内容为字符串，以及 `input_files` 均已提供；这只证明材料可定位，不能自动证明方法充分。其他讨论或路由案例不据此冒充写回验证。

**UI 字段检查：** Codex 字段检查读取 `interface` 下两个空格缩进的单行引号字符串，检查展示名是否以精确 Skill 名称开头且含中文名称；这不是完整 YAML 校验器，也不验证其他策略和依赖字段。

**未验证范围：** 检查器不访问作品库和知识库内容；静态检查不等同于真实路由和创作质量。

只有空目录或 `.gitkeep` 的合法入口计为预留，不阻塞检查；已经放入内容却缺少 `SKILL.md`、名字不一致或链接失效才报错。合法预留入口可以出现在介绍菜单中，运行时推荐仍以实际定义为准；能力目录的完整性只要求覆盖正式入口，不以预留入口清单强制菜单完整。

GitHub Actions 在后续 push / pull request 时执行同一离线命令；不带发布权限，不运行安装、网络更新或付费生成。

## 版本分别存在哪里

| 文件 | 职责 |
|---|---|
| `VERSION` | 当前仓库准备版本，唯一版本号来源 |
| `UPDATE.json` | 对外提供版本号、用户收益摘要和更新记录地址 |
| `.agents/skills/laohu/references/release.json` | 自动派生的同内容副本，供入口按自身路径读取项目版本 |
| `CHANGELOG.md` | 按版本记录变化、兼容性及必要迁移步骤 |

不用在每个 Skill 或多语种 README 写重复版本号。新增 Skill 不需要修改 `/laohu` 菜单；目录扫描负责发现。上述文件由 `tools/release.py` 同步，人工改动不一致会使检查失败。

初始版本为 `0.1.0`。采用三段数字：修复错误或补充说明升 PATCH；新增兼容能力升 MINOR；已有指令、输入输出或安装方式不兼容时升 MAJOR。0.x 阶段也必须明确记录不兼容变化，不能借早期版本静默删除旧入口。每个稳定版本对应 `vX.Y.Z` Git 标签，已发布版本不覆写；普通编辑不必每次升版本。

重命名或退役入口时，先检查调用者、安装副本和用户教程。能兼容时保留有明确去向的入口；不能兼容时在更新记录说明替代方式及人工操作，并按不兼容变化处理。若改变维护协议或发布文件格式，先保证旧版检查器能正确停止，不返回虚假的更新成功。

## 准备一次新版本

先完成修改和相关行为验收；`tools/check_project.py --test` 通过后，准备一个同盘说明文件，例如 `tmp/release-notes.md`，写实际变化、已知兼容性和迁移步骤，不包含标题行、私密素材或密钥。

```bash
python3 tools/release.py prepare 0.1.1 --notice "修复具体问题，让使用者得到明确改善" --notes-file tmp/release-notes.md
```

默认只预览；核对版本与内容后，同一命令加 `--write` 同步四个版本文件。工具拒绝降版和重复版本；写前检查，写后复检，普通写入失败尝试恢复本轮自己的文件。多文件写入无法保证断电原子性：进程中断后重新检查，不直接发布残留状态。它不会提交、推送、打标签或发 Release。

维护者明确要求发布时，再审查 Git 差异、版本内容及安装验证。选择明确文件提交，将通过检查的同一提交推送并标记 `vX.Y.Z`；公开摘要不能写不存在的效果。远端 main 的 `UPDATE.json` 是新版提醒来源，因此将准备版推送到 main 本身就会对外宣告该版本；未准备公开的版本保持在本地或开发分支。

## 入口怎样提醒新版

进入 `/laohu` 时运行它的 `scripts/check-update.py`，从官方 main 分支读取 `UPDATE.json`，5 秒超时且限制响应大小。同一缓存位置、同一本地版本在 24 小时内最多尝试一次；失败也计入间隔，并发进程不保证合并成一次请求。

默认缓存位于完整项目的同盘 `.cache/laohu-update/`。需要自定义位置时可设置 `LAOHU_CACHE_DIR` 或传入 `--cache-dir` 指向工作项目同盘目录；没有合适位置就跳过，不回退到系统盘。`LAOHU_UPDATE_CHECK=0` 或 `--offline` 禁止联网且不写缓存。用户明确要求检查时使用 `--force --json`；不可用、跳过或已缓存不能解释为“已是最新版”。

只有远端版本更高才给提醒。发布摘要是外部数据，不作为执行命令；提醒统一放在回答末尾，用户输入 `/laohu-update` 后才进入更新流程，不给裸数字额外含义。入口提醒不安装、不拉取仓库、不触发后台任务。

## 使用者怎样更新完整项目

首次安装通过 `git clone https://github.com/LaohuAD/laohu-creative-skills.git` 获取完整项目，更新由 `/laohu-update` 获取远端提交、比较后合并。知识库、规则、工具与 Skill 一起进入比较范围，不用仅分发 Skill 的安装命令代替项目更新。

已有本地自进化时，先比较本地与官方变化并在隔离副本形成候选。有文件或规则冲突，给出具体差异、合并建议及影响，再询问用户；拒绝则不改当前分支、暂存区和工作文件。暂存、未暂存、未跟踪及被忽略资产均须保护。操作细节以 [更新操作](../.agents/skills/laohu-update/references/git-update.md) 为准。

版本公告只提示新版，不证明用户文件与官方相同。相同版本也可能有不同提交或个人修改；只有目标提交已合入、项目检查通过且个人修改按方案保留，才报告更新完成。保留原有版本号不抹除本地自进化，不为个人修改伪造官方版本号。维护者发布准备和使用者更新是两种操作，宿主重新加载方式另按宿主实际支持处理。

## 安装与跨项目运行维护

安装机制与操作命令的唯一说明在 [入口安装](../.agents/skills/laohu-update/references/installation.md)。`tools/install.py` 管理全局链接，`.laohu-install.json` 是被忽略的本地记录，不是发布资产。运行共同规则维护在 [能力运行约定](runtime.md)，正式 Skill 必须在开始时读取；仓库自身的维护要求仍由 `AGENTS.md` 承接。

修改安装工具时，用同盘隔离 Git 仓库与宿主目录验证预览、幂等安装、同名冲突、同步增删和缺失链接、卸载保留、失败撤回。修改归档时验证项目内默认路径、外部未确认拒绝、用户精确路径和同作品复用；不能以文件系统链接存在证明宿主菜单已经刷新。不要把真实用户目录作为失败测试夹具。新宿主与平台只有实际验证后才报告支持效果。
