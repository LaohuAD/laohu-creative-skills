# `laohu-motion` 动画技能体验、渐进式全局选型与 WebGL/Three.js 环境优化方案

> **文档性质**：基于 `laohu-analysis` 对当前 `laohu-motion` 体系的代码核查与实测诊断形成的可执行重构方案，供交接 `laohu-evolution` 或工程实施使用。本方案不修改受保护的上游 `templates/runtime/laohu-showreel` 闭包与 `source-lock.json`。
>
> **验证日期与基线**：2026-11-19，基于 `works/video/五层蛋糕·独立输入测试`（499.70 秒 / 231 条双语 SRT）真实运行 `doctor`、`input-prepare`、`input-page` 与脚本源码核查。

[查看本轮实施与验收](#本轮实施与验收)。以下方案正文保留立项时的诊断、基线和验收目标。

## 一、核心诊断：保留什么、改掉什么

本套动画体系的**底层工程与审美基础是优秀的**，但当前把「**扩大模型的审美全局视野**」错误地实现成了「**强制全量灌入 82 页 / 39 万字原文**」，同时把「**防错门禁**」设得过早、过死，外加 macOS 无头渲染下 WebGL 默认参数与 Three.js 离线依赖存在真实环境断点。

| 维度 | 必须保留的优秀机制（不删反强） | 当前真正阻碍能力发挥的根因问题 |
|---|---|---|
| **审美全局视野** | 覆盖全部 75 风格、21 Atlas 家族、240 Motion Prompt、287 OpenMotion、20 Overlay 与共同动作语言的**全库视野**（拉高弱审美模型下限的关键） | 现行 L0 夹带 14 份固定规则重灌（25 页 / 14.7 万字）+ 240 条 Motion Prompt 扁平展开（12.6 万字）+ 75 风格 L1 级冗长描述（10 万字），膨胀到 **82 页 / 39.3 万字** |
| **3D 与着色器能力** | 原版 `stack.md` / `recipes.md` / 风格库对 WebGL 着色器、后期与 Three.js 的支持 | `browser.mjs:28` 在 macOS 硬编码 `--use-angle=metal`，在沙盒/headless shell 下拒绝回退，导致 **`WebGL renderer: none`**；且 `three` 未预装进本地离线闭包，新项目需联网 `npm i three` |
| **人机协作节奏** | 先出差异化方向关键帧 + 3–6 秒动态探针 → 工作台确认 → 再做全片 → 最终预览后导出 | `scaffold` 前置强要求先写完 8 分钟全片完整 `brief.md`（含全部 `<production-units>` 与 462 行双语字幕登记表）并跑完审稿，才能渲染第 1 张方向帧 |
| **文字与字幕品控** | 自托管中文字体、`native-16x9-standard` 固定基线防跳动双语字幕、事实文案受控核对 | 双语字幕被迫重复抄录进 `brief.md` 表格；`runBriefTextContract` 在 `render`/`build` 前单线程逐帧空跑整片（8m20s = **14,991 帧**），长片预检直接变性能黑洞 |
| **迭代与文档结构** | `window.render(t)` 纯函数确定性、共享 `timeline.js` 事件、长片分章缓存 `chapters.json` | 强耦合哈希锁（`designHash`/`projectTreeFingerprint`）导致补素材或微调画面即触发假性失效；旧 Remotion/Film 参考文档（约 370 KB）与新 Showreel 文档混放同目录 |

## 二、方案一：保留 100% 全局视野的「真·渐进式四层加载」（解决 82 页强灌）

### 1. 先看实测数据：82 页到底胖在哪里？

对 `.showreel-input-delivery.json` 与实际输出的 82 页做逐段字符统计（总计含页头约 42.7 万字，纯正文 392,844 字）：

| 内容块 | 现行体量 | 占比 | 问题诊断 |
|---|---:|---:|---|
| 14 份固定规则文档重灌（`SKILL.md` 等） | 147,187 字（25 页） | ~35% | **纯重复冗余**：执行入口本身已按需读取 `SKILL.md` 与 `runtime.md`，重复分页灌入毫无增益 |
| 240 条 Motion Prompt 逐条展开 | 125,942 字（~17 页） | ~30% | **层级错位**：OpenMotion 287 项已按 12 类汇总（仅 ~1,000 字），Motion Prompt 却把 240 条 L1 明细塞进了 L0 |
| 75 项风格丰富字段 | 100,144 字（~14 页） | ~24% | **层级错位**：平均每项 1,335 字（实际是 L1 对比卡粒度），且 32 项 `new:` 风格全标为 `'new Lemo style reference'` 未按视觉大类分组 |
| 21 个 Atlas 家族 | 28,582 字（~4 页） | ~7% | 平均每家族 1,360 字，L0 只需保留家族职责与适用条件 1 行摘要 |
| 20 项 Overlay 表达能力 | 11,892 字（~2 页） | ~3% | 平均每项 595 字，L0 压缩为 1 行速览即可 |
| 共同动作语言（`vocabulary.md`） | 1,618 字（<1 页） | <1% | 精炼有效，保留在 L0 |

同时实测验证：`templates/styles/index.json` 里**每项风格原本就有现成的精炼字段**（`id`、`name`、`metadata.categoryLabel`、`metadata.look`、`metadata.fit`），全部 75 项拼起来仅 **9,019 字**（压缩 **11 倍**，同时 **100% 覆盖全部 75 项风格，一个不少**）。

### 2. 目标架构：真正的 L0 → L1 → L2 → L3 四层渐进加载

核心原则：**「全局一眼全看见（L0），按问题充分展开比选（L1），拟采用项深读全文（L2），写代码按需查源码（L3）」**——既彻底消除弱审美模型「视野变窄、退回套路」的风险，又把开局上下文占用从 **39.3 万字 / 82 轮调用** 降到 **~1.6 万字 / 1 次调用（降幅 ~95%）**。

| 层级 | 内容与覆盖范围 | 目标体量 / 调用次数 | 解决什么问题 |
|---|---|---|---|
| **L0 全局星图（Global Map）** | ① **全部 75 项风格**（按 8–10 个视觉大类分组，每项 1 行：`稳定ID \| 中文名 \| 可见长相 \| 适用任务 \| 渲染技术[2D/SVG/WebGL/Three]`，~9,000 字）<br>② **全部 21 个 Atlas 家族**（每家族 1 行核心视觉机制与成员数，~1,600 字）<br>③ **240 项 Motion Prompt 分类总览**（按现有 15–20 个功能类别汇总，每类 1 行 + 数量，~1,500 字）<br>④ **OpenMotion 287 项 12 类总览**（沿用现有 ~1,000 字）<br>⑤ **Overlay 20 项 1 行速览**（~1,200 字）<br>⑥ **共同动作语言核心表**（~1,600 字）<br>**不再包含 14 份规则文档重灌** | **约 1.5–1.8 万字**<br>（**1–2 页，1 次命令完整输出**） | 让任何模型（包括弱审美模型）在设计前 **100% 看见全库风格与动效边界**，打破单一套路，且不爆上下文、不需循环重定向到缓存 |
| **L1 充分对比层（按视觉问题展开）** | 根据本片要解决的 2–4 个关键视觉任务（如空间层次、信息图解、转场、文字表现），主动展开 **1–3 个风格大类 / Atlas 家族 / Motion Prompt 类别**，或批量拉取 **8–15 个候选条目**的丰富 L1 对比卡（把现行 1,335 字/项的丰富字段下沉到此层，OpenMotion 同时给出 6 格 contact sheet 路径） | 约 1–2 万字（按需 1–3 次调用；**不设 3–5 项上限，支持充分比选**） | 既有足够广度防止「候选太单薄」，又只读与当前片子真相关的候选，把注意力留给审美对比 |
| **L2 完整生产正文** | 对最终拟采用或参与融合的稳定 ID（风格、动效、字体/排印用法），调用 `input-candidate` / `resource-fulltext --level L2` 完整读取正文 | 每项 4–10 KB（通常 2–5 项） | 保留「不从摘要重造算法、按正文真实规格落设计」的硬约束 |
| **L3 实现源码 / Kit** | 进入编码阶段时，按需读取许可明确的本地代码、配方与 OpenMotion 工程文件 | 按需 | 工程落地阶段读取，不提前污染设计阶段 |

### 3. 具体控制点与代码改动清单

1. **`templates/styles/index.json`（及刷新脚本）**：
   - 将 32 项 `new:` 风格的 `metadata.categoryLabel` 从统一的 `'new Lemo style reference'` 细分为真实视觉大类（如 `新闻与调查`、`工程与解剖`、`手作与印刷`、`手绘与插画`、`胶片与复古`、`3D 与微缩` 等），并补充 `metadata.renderBackend`（`canvas2d` / `svg-dom` / `webgl-shader` / `threejs`）。
2. **`.agents/skills/laohu-motion/scripts/laohu-styles.py`**：
   - 新增 `resource-overview --scope global-map`（或升级现有 `resource-overview --scope all --compact`）：输出上述 ~1.6 万字精炼 L0 全局星图，将 240 项 Motion Prompt 按 category 归组汇总（与 OpenMotion 12 类保持一致的抽象层级）；
   - 新增 `resource-compare --ids <id1,id2,...>` 与 `resource-category --source <styles|motion-prompt|atlas|openmotion> --category <类>`：作为 L1 批量展开入口，返回丰富视觉属性、适用条件、融合边界与预览图路径。
3. **`.agents/skills/laohu-motion/scripts/laohu-showreel.mjs`**：
   - 改造 `makeInputBundle()`（`#L904-L994`）：**移除 `docs` 数组中 14 份规则文件的重灌打包**；L0 改为打包紧凑全局星图（**1–2 页**），大幅提高默认分页体验；
   - 新增 `input-map <project>` 一步输出完整 L0 全局星图并写入轻量回执（兼容旧 `input-prepare`/`input-page`，但不再需要连跑 82 次命令）；
   - 保留 `input-candidate` 的 L2 完整正文读取校验，确保采用项仍须真读正文。
4. **规则同步**：
   - 更新 `.agents/skills/laohu-motion/SKILL.md`、`.agents/skills/laohu-analysis/references/motion-design.md`、`.agents/skills/laohu-motion/references/production-collaboration.md`、`.agents/skills/laohu-motion/references/showreel-runtime.md` 中关于「L0 分页 82 页/固定材料打包」的描述，改为「一次性完整接收 L0 全局星图 → 按问题充分展开 L1 候选比选 → 拟采用项读 L2 完整正文」。

## 三、方案二：从根本上修通 WebGL 与 Three.js（不阉割 3D 与着色器能力）

### 1. 实测根因定位（已通过命令复现证实）

本轮对环境做了 4 组对照实测，查明了 WebGL 和 Three.js 不可用的**两个精确根因**：

1. **WebGL 失败根因（不是机器没 GPU，是启动参数把回退路堵死了）**：
   - 受保护脚本 `templates/runtime/laohu-showreel/scripts/lib/browser.mjs` 第 28–34 行写道：
     ```js
     const angle = process.env.SHOWREEL_ANGLE || (process.platform === 'darwin' ? 'metal' : '');
     export const ARGS = [
       ...(angle && angle !== 'default' ? [`--use-angle=${angle}`] : []),
       '--enable-gpu', '--ignore-gpu-blocklist', '--enable-unsafe-swiftshader', ...
     ];
     ```
   - 在 macOS 上该脚本默认硬传 `--use-angle=metal`。当命令运行在 Agent 终端沙盒（限制了 Mach/IOKit 对 Metal GPU 的访问）或 Playwright 默认 `chromium_headless_shell` 环境时，**强制 `--use-angle=metal` 会导致 ANGLE 初始化失败且拒绝自动回退到 SwiftShader**，结果返回 `WebGL renderer: none`；
   - **实测验证**：仅将环境变量改为 `SHOWREEL_ANGLE=default`，同一台机器、同一个沙盒内立刻成功初始化 WebGL2：
     ```text
     [ok] headless browser 153.0.8010.12 · WebGL renderer: ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (LLVM 10.0.0) (0x0000C0DE)), SwiftShader driver)
     ```
   - 同时实测：在沙盒内强制切换完整版 `Google Chrome for Testing` 会因 `ProcessSingleton` 锁受沙盒限制而启动失败；而在**非沙盒普通 macOS 终端**（或用户授权 `BypassSandbox` 执行重度 3D 渲染）下，`--use-angle=metal` 可直接调用 Apple Silicon 原生 Metal 硬件 GPU（速度约比 SwiftShader 快 6 倍）。
2. **Three.js 缺失根因（离线/沙盒不可用）**：
   - 检查 `templates/runtime/laohu-showreel/scripts/package.json` 及 `.cache/laohu-showreel/runtime/` 发现，当前锁定依赖闭包仅含 `playwright` 与 `tone`，**未包含 `three`**；
   - `stack.md:114` 要求每个 3D 项目现场执行 `cd <slug> && npm i three`，这在离线或沙盒环境下必然失败，导致 Three.js 风格成为「纸面可用、现场断链」。

### 2. 根本修复方案（零改动受保护上游 `source-lock.json`）

因为 `templates/runtime/laohu-showreel/` 受 `source-lock.json` 哈希保护，全部修复均落在**本地薄入口 `laohu-showreel.mjs`、`setup` 流程与 `scaffold` 脚手架层**：

1. **WebGL 两档自动探测与自愈（`laohu-showreel.mjs` 的 `runtimeEnv()` 与 `doctor`）**：
   - 若用户未显式设置 `SHOWREEL_ANGLE`，`laohu-showreel.mjs` 首次执行时按当前运行上下文做 1 次轻量 WebGL 探测并缓存（按是否处于沙盒/当前会话环境区分）：
     - **第一优先级（硬件加速）**：先试 `SHOWREEL_ANGLE=metal`；若返回有效 Apple Metal GPU，直接锁定硬件加速；
     - **第二优先级（无缝软渲保底）**：若 `metal` 返回 `none`（例如在沙盒中运行），自动注入 `SHOWREEL_ANGLE=default`（启用 ANGLE Vulkan SwiftShader），确保 **WebGL / Fragment Shader / Three.js 在任何环境下都能 100% 跑通、绝不报 `none`**；
   - 增强 `doctor` 输出：
     - 不再只检查 `getContext('webgl2')`，顺带运行 1 帧 16×16 像素着色器绘制校验（验证真实输出非全黑）；
     - 明确打印当前模式：`[ok] WebGL2: Apple Metal (hardware)` 或 `[ok] WebGL2: SwiftShader (software fallback; 正式重度 3D/Shader 导出建议在非沙盒终端启用 Metal 加速)`；
     - 新增 `doctor --webgl-smoke` 验证 Three.js + WebGL2 实际离屏成帧。
2. **Three.js 预置进本地共享离线闭包（`setup` + `scaffold`）**：
   - 在 `.agents/skills/laohu-motion/` 维护一份独立的本地扩展依赖清单（如 `templates/runtime/vendor-lock/package.json` + `package-lock.json`，不触碰原版 `laohu-showreel/scripts/package-lock.json`），锁定 `three`（含 `build/three.module.js` 与 `examples/jsm/` 常用后期/几何 addons）；
   - `laohu-showreel.mjs setup` 自动将 `three` 安装到工作盘 `.cache/laohu-showreel/vendor/<hash>/node_modules/three`（遵循同卷原则）；
   - `scaffold` 创建项目时（或提供 `scaffold --with-three` / 自动检测 `<direction>` 启用 3D），自动把项目内 `vendor/three` 符号链接或复制到项目本地，并在 `index.html` 注入离线 `importmap`（指向 `./vendor/three/build/three.module.js` 与 `./vendor/three/examples/jsm/`）。
   - 结果：**以后任何 Three.js / WebGL 风格项目开箱即用、零网络依赖、沙盒内也能直接出方向帧和动态小样！**
3. **重度 3D/Shader 导出的性能策略**：
   - 开发、探索方向帧、3–6 秒动态探针：沙盒内走自动回退的 SwiftShader 即可秒级/十秒级完成；
   - 正式长片导出含重度 WebGL/Three.js 时：在提示中引导用户对单条 `build` / `build-long` 授权非沙盒执行（自动走 Apple Metal GPU 硬件加速），兼顾安全与 6× 渲染速度。

## 四、方案三：重排交互顺序——先看真实画面选方向，再展开长片全量设计

### 1. 现状痛点
现行 `laohu-showreel.mjs:1346-1419, 2949` 强制要求「先交齐整片 8 分钟 8 块 XML `brief.md` + 全部 `<production-units>` + 全部 `<screen-text-registry>` + `laohu-audit` 审稿」才能 `scaffold` 建工程、渲染第 1 张方向帧。长片探索阶段成本极高，一旦用户要换风格，返工巨大。

### 2. 优化后的两阶段推进机制

| 阶段 | 目标与门禁 | 产出物 | 耗时与返工代价 |
|---|---|---|---|
| **阶段 A：方向探索与小样确认（`scaffold --phase explore`）** | 仅需：① 已读 L0 全局星图 + L1 充分比选 + 拟采用项 L2；② `brief.md` 写完 `<role>`、`<inputs>`、`<direction>`（含选定资源/视觉语言/色板/字体/镜头性格）及 **2–4 个代表性核心时刻**（无需写完 8 分钟全部分段表与 462 行字幕表） | **2–3 张拉开差距的真实方向静帧（或同方向 3 个代表状态）+ 1 段 3–6 秒核心动效探针**，直接打开本地工作台展示，并同步核对缺失素材（如头像、Logo） | 几分钟内就能让用户看到真画面、真动效；换方向只需改 `<direction>`，几乎零返工 |
| **阶段 B：定案扩片与分章制作（`promote-production` / 正式制作）** | 用户确认方向并补齐必要素材后，在**同一份 `brief.md`** 内补全全片 `<production-units>` 分章导演正文、接入真实音频/SRT 时间轴、运行 `laohu-audit` 查漏，再按章制作与预览导出 | 完整分章工程、`chapters.json`、工作台可播预览与最终 MP4 | 在方向已锁定的基础上精修长片，每一分精力都花在刀刃上 |

### 3. 具体控制点
- **`laohu-showreel.mjs`**：
  - `scaffold` 新增 `--phase explore`（或将「仅含核心方向与代表帧的探索态 `brief.md`」设为合法初始态），放宽 `<production-units>` 必须覆盖全片 100% 时长的校验到阶段 B（`brief-units --final` / 正式 `build` / `build-long`）；
  - 保留方向确认门槛，但把方向确认前移到真正能最快出图的时刻。

## 五、方案四：重构文字合同与哈希锁（救活长片性能与视觉精修手感）

### 1. 解耦双语字幕与 `<screen-text-registry>`
- **问题**：231 条双语 SRT = 462 条字幕被迫抄进 `brief.md` Markdown 表，制造巨大冗余且极易因改一个标点破坏哈希。
- **改法**：
  - **字幕走独立真源**：`<inputs>` 登记字幕文件路径与 SHA-256（如 `input/字幕.srt` 或编译后的 `caption-manifest/2`），`captions.mjs` 直接校验字幕文件与 `native-16x9-standard` profile，**不再要求把几百行字幕逐条抄进 `brief.md` 的 `<screen-text-registry>`**；
  - **`<screen-text-registry>` 只管「屏显主文案与事实文本」**：主标题、章节名、核心论点句、关键数据/专名/账号名（如 `AI造梦师老胡`）仍进登记表，确保事实不出错、字体绑定可核验；纯图形辅助刻度/微标允许标为图形层，不阻断微调。

### 2. 重写 `runBriefTextContract()` 的采样方式（14,991 帧 → ~200 帧）
- **定位**：`.agents/skills/laohu-motion/scripts/laohu-showreel.mjs` 第 599–610 行。
- **现行代码**：`for (let frame = 0; frame < frames; frame++) await window.render(time)`，对 499.7 秒 × 30fps 会空跑 **14,991 帧**。
- **改为智能关键点采样**：
  - 依据登记表每条文字的 `[tAppear, tFullReadable, tEnd]` 自动计算采样时间集合：每条必显文字采 **3 个关键时刻**（刚完整可读 + 中点 + 退场前 1 帧），再叠加每个镜头首尾帧和每 5 秒 1 帧的巡检点，去重排序；
  - 8 分钟片子采样帧数从 **14,991 帧降到 ~150–300 帧**，耗时从数分钟降到 **3–5 秒**，同时精确覆盖每条必显文字的有效阅读窗；保留 `--exhaustive-frames` 选项供短片或专项排查使用。

### 3. 给哈希锁松绑，区分「架构级变更」与「日常微调」
- **定位**：`.agents/skills/laohu-motion/scripts/laohu-showreel.mjs` 第 1518–1635 行、2387–2404 行。
- **改法**：
  - 将 `designFingerprint()` 收敛为只绑定**核心架构项**（`size`、`fps`、所选主方向名、`selectedResourceIds`、`styleframe-source`），不再绑定整份 `brief.md` 全文哈希与整棵项目目录树哈希；
  - 日常微调构图、增补头像素材、修正某段文案、调整动效缓动，不再让「方向确认」反复报错失效；只有**改画幅/帧率、换主风格方向、或最终 `build`/`build-long` 导出前**才执行严格校验与确认。
