# 文件归属、变更与调用依赖

由 [evolution 主文](../SKILL.md) 在判断文件真源、选择新增/改写/合并/迁移/删除、修改多个消费者或维护调用链时读取。它解决已确认改进应落在哪里、依赖怎样更新、运行入口如何读到新内容；读完回 evolution 主文继续写入或融合全流程。本 Reference 不重判专业方法、目标、权限或整体返回条件。

## 找到唯一真源与实际控制点

先沿已确认目标和预期行为检查现有主文、条件读取的 Reference、脚本、配置、模板、评测及调用者。区分说明某规则的文件与实际使它发生的控制点；只改文字而消费者仍走旧路径时，行为不会改变。已有未提交内容、未跟踪或被忽略的用户资产都属于当前实际基线。

按真实维护者和消费者确定文件归属：

| 内容职责 | 优先真源 |
|---|---|
| 当前目标项目的仓库维护要求 | 该项目的 AGENTS.md |
| 老胡能力跨入口的共同运行约定 | 老胡仓库 docs/runtime.md |
| 单个入口的触发、主流程、输出与停止点 | 对应 Skill 的 SKILL.md |
| 宿主内部可组合的子级配置 | 所属宿主目录 `skills/<child-name>/SKILL.md`，由宿主主文选择和加载 |
| 只在某些条件下使用的专业判断或专项方法 | 对应 Skill 的 references/ |
| 确定性转换或可运行检查 | scripts/ |
| 可复现的行为输入与验收条件 | evals/evals.json |
| Codex 展示信息 | agents/openai.yaml |
| 用户作品与生成结果 | 已确认位置下的 works/ |
| 可复用事实、案例、偏好及已验证经验 | knowledge/ |

同一判断只保留一个真源。其他消费者明确读取它，不全文复述。写入 knowledge 的信息只有在可复用且适用范围清楚时才沉淀；当前执行必需的条件要转成运行规则，来源、更新时间及维护追踪细节留在相应台账，不能把待验证经验写成全局路由。

若实施内容涉及另一专业入口的正式产物或写回，先按 `{PROJECT_ROOT}/docs/runtime.md` 核对组合选择、按目标选配授权和产物负责人。文件相邻、同一执行者或必要 Reference 读取都不代替该授权。

## 选择修改、新增或迁移

模仿已有 Skill 架构时，先核对职责章节的实际标题级别与顺序，不额外加总标题使全文降级；只在子项有独立的判断、分支或验收职责时增加下一级标题，不为形式齐全堆叠层级。

设计创作能力的标题骨架时，先按用户起点、所需结果和目标媒介确定输入分支与输出接口，再安排整体构思、分项细化、整体复核与正式交付；标题须指出该节解决的决定、条件或衔接，不以专业分类清单代替创作主线。各分项允许按真实依赖迭代，不把“宏观到细节”写成必须全部定完才能试作的单向流程；输出模板在需求判断时选定，在交付时编译，不到最后才决定产物类型。

用户提供当前成稿并明确要求保留结构时，以实际文件为编辑基线，保留既有标题文字、级别和顺序，只在相应位置补充内容或经允许增加子类。不得恢复此前由 Agent 设计的结构，也不得以整体优化为由移动用户已确定的分类。用户仅要求确定标题或架构时，只输出或写入标题及明确要求的元数据，不填充正文、执行细则、示例或配套运行文件；不能把“丰富”“优化”解释成正文编写授权。交付前与修改前标题序列核对；确有无法在原结构内解决的冲突时说明具体问题，未获结构调整授权前保留原结构。

用户明确锁定 Skill 身份或标题框架时，编辑前从当前实际文件或用户确认稿建立锁定清单，记录 `name`、`description` 的原文，以及既有标题的精确文本、Markdown 级别和相对顺序。只在明确授权的空缺处新增；锁定项与必要改动冲突时，暂停受影响的改动并回到用户授权，不自行优化。交付前用机器逐项对照锁定清单，确认所有获准保留项未变。

先看现有文件是否已经承担该职责，并按部署位置区分公开能力和父级内部配置：

- **修改或重写：** 真源明确且文件可承接时，在原位置改；保留仍有效的目标、偏好、条件、接口、分支和保护项。修补失效方法时同步改变会实际加载它的调用者。
- **命名与部署：** 正式 Skill 命名及宿主前缀按[项目维护命名规范](../../../../docs/maintenance.md#skill-命名层级与部署结构)处理。命名层级与物理部署分开判断；直接部署的公开 Skill 保持公开身份，命名父级不会自动成为运行前置。
- **新增独立公开 Skill：** 只有它需要独立承担完整职责、执行主流程和交付验收，且有公开发现与独立调用价值时，才部署为 `.agents/skills/<name>/SKILL.md`。正式公开 Skill 须有适用的正式元数据、Codex 界面配置和代表评测；其 References 由该入口按条件调用。
- **新增内部子级配置：** 当某些任务需要在宿主完整方法上叠加强制选择条件、且仍由宿主统筹交付时，部署为宿主目录 `skills/<child-name>/SKILL.md`。创建前须按 runtime 的明确专项需求条件界定触发，写出正例、仅材料涉及的反例及无子级的通用路径。配置可限定范围、类别、风格、用途及对应展示或交付要求；必须说明相对宿主默认会改变哪个具体决定或结果；仅未被用户选择及该专项方法固定的变量保持开放。没有独特贡献就留在宿主或 Reference，不为凑层级创建子级。配置不重复宿主的完整通用工作流，也不弥补宿主方法缺失；但凡所选专项方法本身会改变产物，就须在配置中直接承载足以执行该方法的专业判断、步骤顺序、选择分支、必要的固定项、例外和代表性真实案例，不能只写路由摘要并让执行者临场补齐。此处的“配置”描述它在宿主中的部署和调用关系，不限制其承载专业方法的深度。它不自建 References、界面配置或评测；所需的宿主 Reference 由宿主按具体调用链读取。正式文件有自己的 `name` 和 `description`，由宿主定位、读取和执行，不独立注册为入口。
- **配置组合：** 建设内部配置时，写清它限定的维度及与其他配置的组合关系。不同维度可以叠加；不同对象类别可以扩展处理集合；对已选对象添加状态或风格条件不自动取代该对象。用户明确范围优先于默认全量。只有同一对象、同一范围与时点上的互斥取值才构成冲突；不得按加载先后让后一个配置静默覆盖前一个或用户条件。冲突由宿主按用户授权和完整方法处理，无法确定时只暂停依赖该冲突的部分。
- **标题框架草案：** 若当前阶段只确定架构标题，首个 H1 以精确后缀“（框架待填充）”结尾；可以直接从职责章节开始，后续同级章节使用 H1，不强加 Skill 总标题；正文除空行外仅含 Markdown 标题，不写执行细则、正文或占位解释。可按用户明确要求保留仅含有效 `name` 与 `description` 的身份 frontmatter；它只标识草案，不使草案成为正式可执行或可发现入口。不得补写用户未要求的正式运行内容，也不创建空 References、界面配置或评测文件。草案转为正式能力时，移除框架后缀并按公开/内部部署身份补齐正式运行依赖。
- **新增 Reference：** 必须有明确触发、判断方法、产物和读后返回位置；它属于负责其专业方法的二级 Skill。
- **合并：** 重复规则确实表达同一判断时，先确认各消费者如何使用，再把判断集中到一个真源并接好调用；不要只因字面相似合并适用范围不同的分支。
- **迁移或删除：** 只执行用户方案明确包含的文件动作。先保留当前实际内容；搜索旧路径、文件名、标题和链接；保留仍有效内容，先更新消费者，再确认无遗留引用。兼容入口只作明确转向，恢复副本放在不会被发现的位置；不得为了“清理”扩大删除范围。

文件数量、目录层级和篇幅不是质量指标。能由现有文件承接的规则继续放在那里；新增层级资源前先找到其真实读取者。不要建空目录、重复副本或每次执行结果台账来表示尚未接通的能力。

## 安排多文件变更

同一问题涉及多个文件时，按一个变更集合处理：

1. 先读完所有受影响的主规则、References、脚本、界面配置、评测和相关调用者，核实当前未提交状态。
2. 为每条判断确认唯一真源及其消费者，先确定主规则，再定运行时依赖与实施顺序。
3. 规则内容的判断单元拆分、语义对照、MECE范围、增补/分支/冲突裁决、保真及轻量 before/after 映射，统一按[规则表达与方法保留](rule-expression.md#更新规则前按语义对照)执行；本节只把已确认的内容去向落到源文件、目标位置和实际消费者。
4. 按 analysis 已定方案或用户明确选择执行文件动作；内容取舍不由文件迁移顺序决定，未授权不扩大修改范围。
5. 按“运行规则 → 直接依赖与调用者 → 界面配置 → 代表评测”写回；删除或改名之前再次确认没有旧路径消费者。
6. 按上述语义对照完成后，检查文件真源、引用、消费者与评测是否接通。不得把结构完整或映射齐全宣称为行为通过；关键链接、格式、消费者或评测失败时，不能报告变更集合完成。
7. 交付时列清改动、依赖检查、未验证项与实际恢复位置。映射服务于执行和验收，不自动变成每次都要附上的台账；局部失败只处理本轮改动，不回滚他人既有内容。

较大能力重构的规则去向和保真仍按[规则表达与方法保留](rule-expression.md#更新规则前按语义对照)完成；本节再据映射重排文件主线和调用者，不只给旧段落加标题，也不以迁移顺序改动已确认的内容取舍。

## 让每个消费者真正接到文件

任何新增或改动的 Reference、脚本、配置或评测都要从实际入口检查完整调用。调用方应写明：

- 谁执行，什么任务条件触发；
- 读取哪条确切路径和实际范围；
- 资源提供什么决定、方法或产物；
- 读完返回到主流程的哪一步；
- 哪个后续执行者消费其结果。

Reference 不是独立入口时，在所属宿主 Skill 写出这些连接；不要只靠文件存在、目录层级或可点击链接证明已使用。若宿主有内部子级配置，知识塔至少说明每项配置的名称与路径、适用条件、固定或筛选维度、输入依赖、与其他配置的组合关系及返回内容；仅在满足 runtime 明确专项需求条件时由宿主读取；不能把材料出现某对象或读取相关资料写成子级触发条件。宿主按维度关系组合条件、接收结果并处理真正互斥的取值，不得靠加载顺序静默覆盖用户范围。内部子级不得递归调用兄弟配置。任务只读所需内容，不要求所有配置全读或固定组合数量。

### 分层能力的实施验收

每次新建或修改二级/内部三级关系，先核对用户要交付的对象、媒介、已选方法和保护边界，再写调用；不要让复用的旧模板替用户决定成品形式。归属和依赖属于资料关系，不直接决定画面里必须出现谁。例如服装属于一个人物，不意味着服装本体展示必须带人物；具体展示规格从负责能力的字段真源继承。

逐项完成以下对照，任一缺口先修复再交付：

| 必须核对 | 可观察证据 |
|---|---|
| 宿主独立性 | 一个通用请求只用宿主和必要Reference，仍能交付完整结果；不把基本能力拆空后再强制调用子级。 |
| 正向触发与排除 | 用户明确专项请求加载相应子级；相同对象只出现在材料中时不加载；同义表述得到相同处理。 |
| 专业方法与结构保真 | 子级承载所选方法真正改变结果的判断、输入、顺序、选择分支、固定项、例外、停止点及代表性真实案例；保留必要的因果和步骤关系，不缩成类别清单或路由摘要，也不复制宿主完整通用流程。 |
| 判断与触发保真 | 正向触发、材料提及的反例、未选专项的通用路径、选择依据和返回步骤都可从宿主主文及调用资源中直接判断；地域背景、作品名偶然出现或单个效果词不被误当成专项授权。 |
| 风格与固定边界 | 用户明确选择完整风格方法后，保住所选方法的核心固定项、优先级和要求力度；在该方法下有明确适用条件的子模板被选中后，保留其原有条件、顺序、数量与力度。未被所选方法约束的细节保持开放；通用父级方法不得覆盖专项优先级，互斥项交宿主按用户决定裁决。 |
| 案例保真 | 方法要求或来源提供的代表性真实案例须保留其来源、上下文、所展示的具体判断及适用边界；案例要支撑对应的方法选择，不能换成无关材料、只留作者名，或由分析/进化流程原创作品充作教学范例。 |
| 专项贡献与媒介 | 写清子级相对宿主默认改变的具体决定、动作、返回内容和产物位置；对象归属、文本/展示规格及最终媒介表现不互相代替，形式仍服从用户交付目标。 |
| 对象与媒介 | 资产归属、文字规格、展示图的对象分开；图中主体、比例、展示方式及禁止混入的内容符合用户用途。 |
| 约束精度 | 按规则表达 Reference 区分方向与细节；首次构思不强制微观字段，精控/已确认复现/剧情关键条件成立时才展开。 |
| 组合与恢复 | 只组合用户明确选择且维度可并行的专项，资料依赖不引发兄弟级联；同一范围与时点的冲突由宿主显式处理；专项转通用时不残留上轮限制。 |
| 单一真源与消费者 | 主文、子级、Reference、提示词检查与现有评测不相互冲突；同步替换旧要求，不能末尾加一句新规而保留旧模板。 |

把这些条件写入宿主现有评测，并在隔离范围覆盖通用独立执行、专项核心方法、条件模板、专项组合冲突、材料提及、专项转通用及明确的交付例外。案例写可复现的普通输入和可观察判据，不预制作品答案；新增或修订案例不等于已经运行。记录实际读取路径、关键选择、产物和停止点。静态检查只能确认结构，不能证明判断、风格和案例忠实落地。已有不符合新判据的案例须明确修订预期，保留仍有效的身份、连续性、授权与保护条件，不删除案例掩盖失败。

修改能力范围时同步检查 Codex 界面配置：

| 字段 | 项目要求 |
|---|---|
| interface.display_name | 对正式公开入口，以 frontmatter 中实际 Skill name 精确开头，再写中文名称 |
| interface.short_description | 对正式公开入口，用 25–64 个字符准确说明实际用途 |
| interface.default_prompt | 对正式公开入口，一句可直接发送的请求，明确包含 $实际技能名 |

内部配置由宿主负责展示、发现、调用和评测，不为它们创建独立 `agents/openai.yaml`。完整的公开专业能力不因名称层级而成为内部配置，仍按公开入口同步界面配置和评测。已有 policy、dependencies 等配置必须保留。描述与默认提示词随真实能力变化，不替代主文的职责、工作流程和授权边界；不能因某操作需要确认就关闭正常发现。

## 核对运行 Reference 的外链与方法闭合

当运行 Reference 含外部 URL/网页链接，或本次改动涉及专业来源与方法写回时，检查并移除其中的外部 URL/网页链接；保留作者、书名、版本、章节、页码或机构等文字出处，以及原文、译文和本地适配的区别。不要因删链接而丢掉链接承载的方法：把已选方法、适用条件、步骤、判断、例外和必要的本地用法写在 Reference，让执行者无需打开网页补足专业依据。仅确认 URL 数量为零不足以证明完成；还要从普通任务输入走读，确认能凭本地方法得到预期判断，并保留原有停止、例外和不推断边界。

建设阶段可以访问来源核验内容。若某项任务本身要求核实最新事实、检查新作品或进行用户指定研究，按其任务范围与授权查证；不要把这与运行 Reference 依赖外链补方法混为一谈。此项不要求全仓禁链脚本，也不替代对项目内 Markdown 相对链接的检查。

## 核对仓库内链接与路径

执行前将运行时占位符按 `{PROJECT_ROOT}/docs/runtime.md` 定义解析到真实目录；占位符用于 Agent 路径表达式，不能当 Markdown 本地链接目标。Markdown 点击链接一律以包含该链接的文件位置为基准，逐条核对相对层级及 URL 解码后的实际路径；移动 Markdown 文件后重新核对它发出的链接，移动被链接文件后搜索所有旧目标并更新消费者。项目检查可以发现支持范围内的本地路径错误，但不能证明外部网站内容或适用性、锚点或实际运行有效。运行 Reference 的外部 URL/网页链接按上一节处理，不保留为方法依赖。
