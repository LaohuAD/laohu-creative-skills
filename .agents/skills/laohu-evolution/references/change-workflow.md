# 能力文件增、改、删

由 `{SKILL_DIR}/SKILL.md` 第 3 步在选择文件、增改删、迁移内容、追踪多个消费者或修改调用链时调用。它解决已定改进应落在哪些文件、如何到达实际执行位置及如何检查依赖；读完返回主文第 4 步实施。接收依据、实质判断和暂停/返回 analysis 的规则只以主文第 1、2 步为准，本 Reference 不重复裁决。

## 从预期行为找到实际控制点

1. 承接主文中的目标、已定依据、预期行为变化和要保护的有效旧行为。对目标文件及其真实调用者做最小检查，确认文件内容仍对应已批准条件；不重查根因。
2. 找出谁实际消费或执行该行为：入口 Skill、条件读取的 Reference、脚本、配置及调用它们的其他入口。区分“描述规则的文件”和“实际控制行为的文件”。如果只改说明不会改变执行结果，就把改动落到真正控制点，并同步因此受影响的调用方。
3. 按谁消费、谁维护判断选择唯一真源：目标仓库维护规则归其 `AGENTS.md`，老胡跨入口运行规则归 `{PROJECT_ROOT}/docs/runtime.md`；单一入口的触发、输入、动作、输出和停止点归其 `SKILL.md`；条件方法归该入口的 `references/`；稳定转换或检查归 `scripts/`；可复现行为样本归 `evals/evals.json`；Codex 展示信息归 `agents/openai.yaml`；作品与生成结果归 `works/`，可复用事实、案例、偏好和已验证经验归 `knowledge/`。不要把同一判断散写在多个地方。

## 选择文件动作

先选择实际承载能力的内容：判断与条件由规则和 Reference 承接，具体表达由完整案例承接，进入成品的模板与样式可放该 Skill 的 `assets/`，确定性转换用 `scripts/`。仅在确有可使用内容时创建，不能建空目录表示已具备能力；模板不冒充方法，目录存在不等于消费者已经读取。

顶层只保留所有入口共同需要的目标、权限、路由、资产归属和交付责任；单项执行方法与格式移到真正负责人，不为压字数丢掉条件，也不把长文拆成互相依赖的小碎片。新增专业方法先看现有 Reference 能否承接；独立且反复使用才另建，并在主文写明调用条件。

涉及安装或副本时核对真实路径与发现入口。保留一个实际方法真源；兼容入口只做明确转向，恢复副本放非发现位置。修复已完成的重复发现不重复复制或删除公共技能，跨项目变化仍按当前授权处理。文件体量用于定位职责混杂，不是长短质量阈值。

- **修改**：已有文件实际拥有该职责且结构可承接时，在其当前组织中改写或增补；保留与新改进兼容的有效行为和条件，并检查所有受影响消费者。
- **新增**：现有文件没有承接该独立职责的真源，或放入其中会让不同执行者、触发条件或维护职责混在一起时，创建有明确使用条件的文件，并接好所有调用方。只有触发条件、判断过程、交付物和完成证据独立且会重复出现，才新增 Skill；提供可执行的主文、按本文件“Codex 中的技能展示”配置的界面元数据和适用评测，不留空骨架。
- **删除或迁移**：仅在实施依据已包含相应文件动作时进行。先备份目标；搜索旧文件名、路径、段落标题和链接；保留已确定要继续生效的内容；更新消费者，再确认没有遗留引用。不要用添加例外的方式掩盖已确认要修复的冲突。

## Codex 中的技能展示

本项目每个正式 Skill 都须提供 `agents/openai.yaml`，包含 `interface.display_name`、`interface.short_description` 和 `interface.default_prompt`。`display_name` 统一写作“`SKILL.md` frontmatter 的实际 `name` | 中文名称”，前缀须与实际 `name` 完全一致且只出现一次；中文名称面向用户。简短说明用 25～64 个字符描述实际用途；默认提示词用一句可直接发送的请求，并明确包含 `$实际技能名`。字符串加引号，内容与当前能力一致；预留空目录不生成界面配置。这是本项目约定，不是所有 Agent 的通用必需格式。

新建老胡入口时在主文开始接入 `{SKILL_DIR}/../../../docs/runtime.md`，已加载则复用，不依赖先调用总入口。新建、迁移或改变能力范围时同步维护这三个字段；已有 `policy`、`dependencies` 等无关配置必须保留。默认允许自动发现，不因需要用户确认某项操作就关闭隐式调用。界面元数据不替代 `SKILL.md` 的发现描述、工作流程和授权边界。

## 多文件变更

一个问题同时影响两个或以上文件时，按一个变更集合处理，不把每个文件当成互不相关的修补：

1. 先列出主规则文件、运行时直接读取的 Reference 和脚本、评测样本、路由或公开文档，以及它们之间的依赖关系。
2. 为每个判断指定唯一真源；先改真源，再同步依赖文件，不让派生文件反过来覆盖主规则。
3. 先读取变更集合中的所有相关文件，再编辑；发现未提交的用户改动时保留并合并，不用整文件覆盖。
4. 按“规则 → 运行时依赖 → 评测 → 路由与公开文档”的顺序写回；任何关键引用、格式或评测失败，都不能把集合标记为完成。
5. 涉及重命名、删除或移动时，先全仓搜索旧路径和入口；只有确认没有外部调用，或已提供兼容入口，才移除旧位置。
6. 交付时列出变更文件、依赖检查、未验证项和恢复方式。一个文件失败时，只撤销本轮自己的变更，不能回滚用户已有资产。

如果多个文件分属不同专业领域，`laohu-evolution` 只负责范围、依赖和写回协调；专业判断交给对应 Skill，不把领域内容硬塞进顶层规则。

## 接通每个消费者

任何新增、移动或改动的 Reference、脚本或配置，都从实际入口检查调用闭环。调用方须说清五件事：谁执行、何时触发、读取哪条明确路径、该资源解决什么判断或提供什么产物、读完返回哪个执行步骤并由谁消费其结果。缺一项就补到真正调用方；只有文件存在或链接可点，不代表已接入。主文中的 `{SKILL_DIR}` 和 `{PROJECT_ROOT}` 按 `{PROJECT_ROOT}/docs/runtime.md` 定义解析，并核实实际目录，不依赖终端当前路径。

编辑完成后按变更类型检查真实引用和消费者；若更新了项目工具，按主文运行对应测试。所有路径包含空格时在命令中正确引用。实现中若发现内容层面的新矛盾，回到主文第 2 步交 analysis；不要在这里自行裁决。
