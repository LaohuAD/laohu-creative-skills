# 老胡能力进化

**已确认的方法写进实际运行链，改进才会留在下一次任务里。**

## 核心职责与边界

**专业取舍由已确认方案决定，文件与调用由本入口接通。**

把已确认的能力目标、专业方法和关键取舍写进未来执行者会实际加载或运行的位置，让普通请求能沿最终文件完成工作。实施者负责核对现状、判断真正控制行为的文件、保留或整理原有内容、改写运行方法、接通消费者、同步适用的界面与评测，并完成授权范围内的结构及实现检查。

本入口实施长期能力，不替用户重新裁决未定的专业方法、范围或关键取舍；这些判断会改变规则时，带着缺项和影响交回 analysis。文件位置、段落组织、自然措辞、引用接入及其他可恢复实现由本入口负责，不把普通编辑推回 analysis。当前作品、封面、图片、视频与提示词成品由适用专业能力完成；文件关联不自动产生跨入口授权。

已定方法或经用户明确选定的政策可以实施。分别标明已选定的规则和已验证的效果；不因尚无本地数据而阻止经授权的可恢复试用，也不把试用预期写成结果。外部报告、理论名称或他人意见不代替已确认依据；用户明确要求跳过分析并亲自选定规则时按其决定执行，同时保留它尚未被外部依据验证的身份。

每个独立公开 Skill 的主文必须保留统领专业工作的判断、完整主要步骤和步骤衔接；Reference 深入可独立调用的专业方法或分支，不能成为只供引用的知识摘录，也不能改写上游目标、权限、入口职责或全局返回条件。新增或调整公开能力、内部配置或其交接时，按 [能力文件增、改、删](references/change-workflow.md) 确定部署和职责边界，并执行其中“分层能力的实施验收”：检查宿主独立完成通用任务、用户明确专项触发、子级对实际产物的独特贡献及全部消费者一致性，再按运行约定接通真实消费者。

## 选择局部修改还是整体重构

**改动范围跟着真实缺口走。**

按已授权范围判断改动大小，不按文件数量或文字长度判断：

- 用户给出确定文字、路径、已知修法或单点接口修复，且其他职责与依赖不需调整：完成对应局部修改。
- 用户要求新建或整体重构能力，或核心职责、主要方法、Reference 分工与消费者彼此牵连：按完整设计实施，保证从目标、架构、分项方法到最终交付接成一体。
- 修改过程中发现必须重选的目标、权限、核心方法或关键取舍：只暂停依赖该项的写入，将具体材料、影响和待决问题交 analysis；其余已授权且不依赖该项的内容继续。

一次小改动不自动启动全面设计；一项完整能力也不能靠给旧段落加标题冒充重构。范围大时先确认它确实响应用户已选的方案，再按后文全流程落实。

无论改动大小，只要会新增、修改、融合或移除运行规则，在决定内容去向前先读 [规则表达与方法保留](references/rule-expression.md#更新规则前按语义对照)。该 Reference 唯一规定新旧判断的语义对照、MECE 范围、冲突裁决和信息保真；涉及多文件、迁移或消费者变更时，再读 [能力文件增、改、删](references/change-workflow.md) 安排文件映射和调用顺序，不重复建立另一套内容比较表。

## 进入实施并核对现状

**先认清当前文件实际控制什么，再动手。**

沿用已有任务状态和用户的授权，不重复询问已确定事项。先确认目标项目和真实 Skill 目录，读取目标主文、本轮会影响行为的 Reference、实际调用方、配置、脚本和相关评测。结合失败产物或反馈记录，沿请求触发、资源读取、关键决定、执行动作、下游消费与最终产物追到第一处未按已确认目标传递的控制点；方法存在但该次未读取或未执行时先修调用；规则本身已确认缺少必要方法时可补齐；完整执行后目标仍未达成或适用条件过窄时，交 analysis 重看方法与条件。凡拆解、吸收或写回既有规则/专业方法，即使没有“写弱”反馈，也按[规则表达与方法保留](references/rule-expression.md#回核原始意图与既有规则的偏移)先还原本轮有效决定并核对旧控制点；当前明确澄清可直接作为决定，旧文不能自证原意。文件存在、链接可点或规则文字完整，都不证明下游已调用它。

编辑前按 [运行约定的过程文件存放规则](../../../docs/runtime.md#过程文件与恢复副本的存放) 确定当前项目内的恢复与验证位置，再保留目标目录当前实际内容及可恢复路径，尤其保护未提交、未跟踪和被忽略材料，不能只把 Git HEAD 当作备份。建立简短工作映射：本轮目标、现有控制位置、保留内容、要改或合并的内容、依赖和预期观察。不要另造只供归档的报告。

整体重构或跨文件迁移时，将原有判断单元映射到目标位置和实际消费者，并按已确认方案落实保留、替换、增补、合并、分支或删除。专业内容的取舍依据由 analysis 或用户已选方案确定；本入口不机械保留全部旧文，也不自行删除、改弱或重判实质方法。对移动、删除和多文件依赖，按 [能力文件增、改、删](references/change-workflow.md) 搜索现有消费者并安排先后；写入方法与表达时按 [规则表达与方法保留](references/rule-expression.md) 保住已选判断的条件、作用和承载形式。取舍尚未确定且会改变运行时，带着具体差异返回 analysis，不让两个相冲突的指令并存。

## 逐部分写回已确认方法

**每个步骤都要有输入、决定、动作和去处。**

有完整设计依据时，依其整体结构逐部分落实：每个环节说明输入、决定条件、动作、中间产物、下一位消费者、分支和停止点；再把它们接成目标领域主 Skill 的专业主线。只修改说明而不改实际调用者，或把需要生成的专业产物留给未来执行者猜，都不算完成。无需用形式相同的标题复制设计顺序；根据该能力真正的分工组织主文与 Reference。

将已确认的作品用途、作者表达意图与读者要求写进实际的生成步骤和成品验收：按真实使用情境落实接收者需要理解、感受或采取的行动，并保留作者已选的立场、视角、声音、情绪力度、技法与优先级；若原规则可能在转写中走弱，按规则表达 Reference 回查证据，不从旧文或个人偏好推断。再选择相应体裁、语言、组织和版式。不同产物按实际需要确定形式，不预设封闭类别或统一报告模板；源头规则的表达方式不会自动成为目标作品的语体。最终产物服务人的阅读或使用，需要机器读取的部分继续遵守精确接口，不用解释文字破坏契约。创作能力的层次定义只沿用 analysis 的 capability-design；面向读者的价值选择或文字成文能力改造时，按需读取根目录共享 Reference，并把方法写入真正会被目标 Skill 加载的执行步骤。本入口的 rule-expression 是规则建设方法，不是普通创作任务的运行指南。

写入或迁移运行规则时读取 [规则表达与方法保留](references/rule-expression.md)，处理方法、出处、语言力度、正例和 Markdown 组织；完成后返回本节实施。它是运行规则保真和表达形式的唯一维护细则来源。专业四层的定义只由 analysis 的 capability-design 维护，evolution 负责将已选关系接入规则和实际产物，不复制第二套定义。目标能力要交付文字时，按需读取[语言成文方法](../../../references/language-realization.md)，并检查目标主文或实际 Reference 是否让普通成文路径使用相应动作；目标以读者接收价值作取舍时，按需读取[读者价值与作品组织](../../../references/audience-value-and-structure.md)。

创作与审美规则采用用户指定的“现代汉语的诗学箴言体”：原则句凝练、有方向、有分量；机制解释材料关系与边界，执行步骤把取舍落到动作，成品验收负责纠偏。四者相互承接，不是每段要填齐的栏目；原话完整保留在 Reference。普通操作、事实、权限、文件路径与停止条件用准确直白的现代汉语。章节帮助扫读，段落只讲清一项中心，真正关键的判断加粗，表格只呈现真实对照；不设字数限制，也不把每节硬凑成格言。

把已选方法写进实际运行规则时，优先保留用户给出的准确适用原句、标准术语和核心命题，并让它们承担真实判断；写在目标 Skill 主文或实际读取的 Reference 里，不只存进背景资料。原句或术语已能指导本地选择时直接使用；只有迁移后仍有歧义或执行缺口，才补足必要的本地条件、动作或取舍，并标清来源原意与适配。外部引文先核对原文与上下文，按版权作必要短引并注明出处；无法核验时明确转述，不冒充原话。保留原方法的优先级、步骤、条件、舍弃对象和力度。直接复用不等于免于理解、来源归属核验或适用性判断；来源待核只限制出处、原文归属及外部事实/效果断言，不改弱用户当前明确给出并选定的方法。analysis/evolution 的规则、方案和解释可以原创组织，但不得自行创作作品充当专业示例、演示、临时试作或验证结果；例子来源、上下文、适用边界和效果证据由 [规则表达与方法保留](references/rule-expression.md) 唯一规定。来源暂缺时把缺口放入分析交接或已有来源/验证记录，继续落实已确认的方法；只有方法内容或适用条件本身不清且会改变动作时才暂停依赖部分。经授权的目标执行 Skill 可以原创用户实际要求的作品；evolution 只核对它是否按最终文件执行，不代写该作品，也不把本次执行产物升级为正式范例。

研究和建设阶段可以访问外部来源核实材料；写入运行 Reference 时，把已选方法、适用条件、步骤、判断、例外和必要的短引或本地用法写在本地，不保留外部 URL/网页链接，也不要求执行者点开来源来补足方法。作者、书名、版本、章节、页码等书目信息，以及原文、译文和本地适配的区别，仍按规则表达 Reference 保留。来源无法核实时，只对出处归属、原文/来源原意及外部事实或效果断言标待核或收窄；用户当前明确给出并选定的方法仍按确认范围落实。方法内容或适用条件本身缺失且会改变执行时，才暂停依赖部分并回 analysis；状态记录放在分析交接或已有来源/验证记录，不在规则或成品附加“仅供参考、未验证效果、可尝试”等削弱语。这条不禁止任务本身需要的时效事实核查、新作品核验或用户指定研究；是否查证由该任务的目的和授权决定，不由 Reference 为缺失的方法内容派发网页访问。

## 整合主 Skill 与整体执行链

**各部分写得正确，还要能合起来完成同一个任务。**

完整重构不是逐份 Reference 各自改好就结束。把已确认的目标、专业判断和主要步骤重新写入目标 Skill 主文，让普通请求能沿一条完整路径走到目标产物；把分散在多处的同一判断合并到唯一真源，再让各章节和 Reference 按条件接续。

用至少一项普通任务做方案走查，从入口推演到应有的完整局部产物：检查每一步的决定是否发生在需要它的位置，中间结果是否被下一步实际使用，条件变化是否进入正确分支，整体交付是否保留目标、偏好、事实与权限边界，并适合真实读者的理解、感受或使用。方案走查不生成作品示范。若作品行为需要验证，在用户授权范围内由目标执行 Skill 仅凭最终交付文件和普通任务输入实际产出，再检查体裁与形式是否服务用途、保护项是否保留及必要机器接口是否完整；evolution 不代替目标 Skill 创作作品。对局部修复，只检查受影响的路径及必要近邻，不强制重建整条能力。

如果章节顺序、触发条件或 Reference 调用需要改变才能让全流程成立，就直接重排主文和调用关系；不要把旧段落原样铺开，只为它们添加更多标题。完整流程仍应允许局部请求跳过无关步骤，只有真实依赖决定先后。

## 接通文件、界面和评测

**规则真源唯一，消费者逐个接好。**

多文件修改是一组变更：先明确唯一真源，再按“运行规则 → 直接依赖与调用方 → 界面配置 → 代表评测”同步。改主文时确认它在何时加载哪些确切 Reference、Reference 解决什么判断、读后回到何处；同步现有消费者，不重复维护整套规则。新建文件须有独立职责和真实调用者。用户要求公开能力范围变化或整体重构时，对所有正式公开入口（无论名称层级）同步核对 `agents/openai.yaml` 的展示名称、说明与默认提示词，并维护能代表其独立工作的 `evals/evals.json` 案例；内部部署配置不单设界面配置或评测，其选择行为由宿主入口的案例覆盖。不得删除或弱化已有案例来隐藏失败。

创作或表达规则写作需要保留专业例作时，按来源门处理；要给实现者的产品规则、机器字段或固定输出模板时，保留精确接口。不得把资料、样例、内部审核过程或猜测写进最终成品，除非用户明确要求该内容作为交付。

## 按证据验收并交付

**检查通过到哪一级，就只报告到哪一级。**

按变更类型分别检查真实路径、引用、格式、调用和受保护内容。维护老胡仓库时，交付前从已核实的根目录运行 python3 tools/check_project.py；脚本、发现或版本逻辑变化时，另按 maintenance 要求运行离线回归。不要准备版本、提交、推送或发布，除非另有明确授权。

验证 analysis 或 evolution 等元入口时，分两段检查：先用最终 analysis/evolution 从普通需求实际建立或整体改进一个目标执行 Skill；再由另一位未参与目标能力设计、未见该新样本设计过程的执行者，仅凭最终目标 Skill 文件和新的普通输入，实际执行该 Skill、独立完成下游任务并交付完整产物。若下游产物是创作作品，必须由目标执行 Skill 按其最终文件生成，元入口不得代写或把作品演示当作验证。若运行中追加的聊天指导补出了文件没有提供的核心目标、取舍、方法或验收，该次产物只能说明在额外指导下的表现，不能证明文件独立生效；按[判断、运行与下游产物验证](../laohu-analysis/references/validation.md)记录指导内容和影响，写回已确认方法后须另用无该指导的普通输入复查。只看方案、文件结构、同一设计样本或修改者自评，都不能证明元入口已把能力建设交给未来使用。

对非元入口目标能力的方法或行为作实质改进时，需要由未参与候选设计的执行者仅凭最终主文、实际会读取的 Reference 和普通任务输入，独立生成下游产物。检查条件变化会不会改变选择，下一步是否真正使用前一步产物，保护项是否保留。静态检查最多证明结构；走查最多证明方案可接手；一次试跑不自动证明稳定性或真实质量。按项目定义报告 STRUCTURE、ROUTE、BEHAVIOR、QUALITY 状态；未执行的行为写明未验证，真实接收者或使用结果缺失时质量为 UNKNOWN，代表产物已经显示目标未达到时为 FAIL。

交付时说明实际修改路径、各文件承担的职责、保留/重写/合并/迁移/删除的范围、检查结果、未验证项和可恢复位置。行为验证由独立执行者报告时，区分其观察与结构检查，不将未完成的结果写成通过。
