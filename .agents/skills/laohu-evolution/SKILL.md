# 老胡能力进化

`{SKILL_DIR}` 是本文件所在目录的真实路径（解析符号链接）；`{PROJECT_ROOT}` 是解析 `{SKILL_DIR}/../../..` 后的项目根目录。执行命令前核实根目录实际包含 `AGENTS.md` 和 `tools/check_project.py`，并替换占位符。

## 职责

把已确认的能力改进完整落实到实际执行会读取或运行的位置，使预期判断与下游产物真正改变，同时保留有效的旧行为及其适用条件。接收用户已选定的具体实施方案或 `laohu-analysis` 已确认的结论；不重新调查原因、判断专业方法真假或决定哪些实质内容值得保留。当前作品及其图片、视频、封面和提示词成品交给对应专业入口。

本入口解决“已选做法怎样完整进入真实执行，并能独立产出所需结果”。必须自己完成规则表述、文件组织、依赖接入、必要示范和实现修正，不能把这些再推给 analysis。只有缺项会改变专业方法、核心范围或关键取舍时才返回判断；退回带具体缺项与影响，保留其他已完成内容。

## 执行

1. **接收和校准依据。** 用户明确要求维护未来可复用的能力时继续；一次性作品修改交给对应入口。用户选定的具体方案或 analysis 已选定的实施路径可执行；未经选择的备选和待决内容不冒充定案。有依据且已在授权内选定的候选方法可制作可恢复版本并试用，“选定实施”与“效果已验证”分别说明，不以尚未证明本项目效果为由阻止试用。先检查结论的对象和适用条件是否仍对应当前文件与运行路径。这是实施前的范围核对，不是重新调查根因。

   对于要解决问题的 analysis 交接，先确认方案已具体到可落地：真实控制位置与增/改/删内容明确；核心规则有可采用且含条件和要求强度的文字，专业选择、关键分支和目标效果明确；保护项、实施顺序/依赖及可观察验收已交代。这里只核对交接完整性，不重设计专业方案；具体措辞、章节、示范制作和接入由本入口完成，不要求 analysis 先写完每个字符。缺少会改变目标、授权、专业方法或关键验收的内容时，列出具体缺项及影响，暂停依赖该点的写入并返回 analysis；其他措辞、结构和可恢复实现由本入口决定并继续。不得用“优化一下规则”代替方案，也不把待决定事项当成已确认。

   用户说“同意外部报告”或“按报告改”，不等于报告已通过 analysis 核对。若报告、其他 Skill 的建议或用户对原因的解释将决定规则内容、方法、范围或例外，而这些实质判断未定，建议先交 analysis 核对并暂停依赖它的部分；用户已授权你调用时，读取 `{SKILL_DIR}/../laohu-analysis/SKILL.md`，交接具体待判项，不得声称尚未发生的调用。用户明确要求跳过 analysis 并亲自选定了具体规则时，可按授权实施，但说明这是用户选择，不代表外部依据已核实。已确定的路径、文案、格式和不依赖待决实质判断的技术操作可直接完成；不要把附带的原因猜测写成事实。

2. **核对现状和落点。** 已有 Skill 的升级或经验注入，按顺序读取：先明确要修改的目标项目，读取该项目适用的 `AGENTS.md`（存在时）和目标 Skill 的 `SKILL.md`，不把能力安装仓库自动当作修改对象；再读目标 Skill 本轮需要的直接引用、脚本、模板和评测；再读产生反馈的作品、失败输出或变更记录；只有迁移成熟机制时才读外部项目对应真源和验证记录。检查目标文件、已确认条件和当前消费者；找出实际控制预期行为的入口、规则、脚本、配置及所有必要调用方。用简短的工作映射对齐：目标与已定依据、预期行为变化、要保护的有效旧行为、真正需要改动的控制点。无需另建映射报告。不能只改解释文字而漏掉实际入口或运行文件。

   若检查发现目标冲突、授权变化，或缺少会改变核心规则/专业方法的判断，暂停依赖该问题的写入；不受影响的工作继续。常规措辞、结构、配置衔接和可恢复实现由本入口决定，不因没有专门标准而暂停。将冲突与材料路径、影响、需要 analysis 决定的问题、可继续部分和返回后接续步骤交回 analysis。不要自己补理论或扩大成全面审查。

3. **按需读取实施 Reference。** 当要选择/增改删文件、迁移内容、改变能力范围或界面配置、追踪多个消费者或修改调用链时，由实施者读取 [能力文件增、改、删]({SKILL_DIR}/references/change-workflow.md)，用它定位真源、实际执行者和依赖，执行其中适用的界面配置与多文件变更要求，再回到第 4 步完成实现。当要新增/改写运行规则、迁移已确认的方法或较长流程、或制作可复用的成品示例时，读取 [规则表达与方法保留]({SKILL_DIR}/references/rule-expression.md)，按其中四层能力检查、规则编译与方法保真要求写入，再回到第 4 步。普通单文件路径、措辞或配置修正无需读取方法 Reference。未来使用该能力的执行者，须能凭正常任务输入及随能力交付且实际加载的文件完成工作；本次已确认的聊天方案应编入运行文件，不能让未来执行依赖制作聊天。References 不重新决定接收依据、暂停条件或返回路由；这些以本主文为准。

4. **实施并串起行为链。** 先按表达 Reference 恢复完整有效方案，将每项已定要求对应到实际规则、消费者和检查；先前讨论中的条件、强度、例外与示范作用不能被最近摘要覆盖。逐项核对遗漏后，再从已确认的输入开始，保证每个必要步骤都有执行者、可检查产物、后续消费者、适用分支及失败停止/返回方式；修改所有使预期行为生效的文件和调用方。涉及规则文字时，按第 3 步加载的表达 Reference 确定文字作用、编写并删并，再核对示例；方法细则只在该 Reference 维护。本步骤不重判已确认的专业方法。具体措辞、章节组织和成品实现属于本入口责任，不能用“表达偏好”或“需要再分析”回避。已确认目标明确而候选实现没有达到目标时，修正实现；只有目标冲突、强度/适用范围未定会改变行为，或专业方法本身缺少关键判断（例如未定义的证据评分规则）时，才回到第 2 步，按第 1 步路由交 analysis。普通表达和实现选项由本入口作明确、可恢复的选择；成熟经验可作有边界的默认实现，不伪称用户政策或已证实事实。不得把用户已确认的风格改得更温和、中性或弱化。

5. **按变更类型验证。** 路径、格式或文件动作检查真实引用和调用链；路由变更检查正确请求、近邻反例及项目实际发现；方法迁移检查代表性输入到产物、关键分支/例外/失败路径和应保留的旧行为；脚本变更实际执行成功与失败路径。规则表达变更还须检查：关键对象与动词是否明确，术语是否带来可执行判断，必要解释是否仍有作用，重复内容是否归并到唯一权威位置，正反例是否与规则一致。方法、表达或交接规则改动后，在选取试跑样本前读取 `{SKILL_DIR}/../laohu-analysis/references/validation.md`，按其定义区分示例复现、旧行为回归和留出验证。还要由未参与候选设计的执行者，用正常任务输入实际加载最终交付的 Skill 和所需 References 试跑，确认产物能从这些文件独立产生；不提供制作聊天有助避免提示，但不自动构成留出验证。需要检查迁移时，另选未参与候选设计、对象及关键条件不同的留出样本；旧版新版都通过只证明原行为保持，不证明能力改善。目标效果是否达到与保护项是否保留分别检查；若代表样本已显示已确认的预期效果没有出现，这是 `FAIL`，不能用质量证据不足改报 `UNKNOWN`，也不能报告本轮完成。只有真实接收者或实际使用质量尚无证据时才标 `QUALITY UNKNOWN`。创建或实质改进能力时还须按该验证 Reference 用普通需求建立或改进目标能力，再使用最终文件产生下游完整局部产物；不以文件完成替代用户结果。需要比较旧版时使用改前实际快照，读取变动中的当前文件不算旧版试跑。根据实际执行证据说明结构是否完整、哪些样本行为通过、真实使用质量是否未知；checker 通过本身不证明行为或质量提升。

   维护老胡仓库时，实施前读取 `{PROJECT_ROOT}/docs/maintenance.md` 的本地检查要求，交付前从已核验的仓库根目录运行适用检查；准备版本时再读其版本与发布部分。修改其他项目时读取并执行目标项目的维护与验证要求，不在老胡安装仓库运行无关检查代替目标验收。本文件不重复维护检查命令。

   关键要求都须对应到实际控制点和相应检查证据；出现关键失败时不能报告完成。若样本显示实现偏离已确认方案，修正实现并重跑对应检查；若方法完整执行仍未达到目标，返回第 2 步交 analysis 重查方法与条件；输入、环境或评价无效先修复相应部分，不把所有失败归咎规则。没有真实使用或接收者反馈时，质量标为 `UNKNOWN`。

完成后在聊天说明实际改动路径、实现到哪些执行位置、验证结果和仍未知之处。仅将有长期回归或维护价值的方法、输入和观察保存在既有职责位置，保留适用条件；替代旧做法时合并或删除失效补丁。默认不创建每次执行的结果 JSON、哈希报告、审计日志或空目录。
