# 已确认问题的表达方式

由 `{SKILL_DIR}/SKILL.md` 的“表达已确认的问题”在问题已确认、准备写问题包时读取。执行者是本次 audit 检查者；本文件只把既有观察和目标差距写得直白、有质问感，不负责发现或确认问题。读完返回主 Skill 的“表达已确认的问题”，检查通过后再进入“输出问题包并停止”；表达不改变问题状态、排序、证据范围或授权。

## 从证据找到锋芒

专业缺口的锋芒来自指出执行者被迫补造的具体工作。例如，只有在候选承诺优化开头、正文和全部直接依赖均只有“素材不足就补充、增强吸引力”时，可写：“这里把‘补素材’三个字交代了，去哪找、挑哪条、怎么写进开头，全留给执行者现编。所谓优化方法，到底提供了哪一步？”它指出已核对的方法缺失，不指控作者动机，也不预测播放量。若方法实际在 Reference 中，撤回这项缺陷，不能为了保留狠话忽略反证。

先锁住四个已确认事实：具体位置、材料中的实际观察、对应的已知目标、两者之间的差距。锋芒只从这条关系里来，不从作者身份、猜测动机或审查者情绪里来。

优先抓材料自身最清楚的落差：

- 前后两条要求互相打架；
- 明确目标说要做到什么，实际对象却显示了相反结果；
- 流程某一步跳过了它承诺要完成的动作；
- 标题或说法作出一种承诺，实际内容交付了另一种东西。

把落差压成自然口语，明确点破已确认的缺陷，并以有依据的讽刺评价和追问传达锋芒；讽刺与追问可融入同一句，不固定先后顺序。默认目标是贴吧老哥式毒舌：挑剔、不客气，允许挖苦责问；标题、正文或追问自然落到已确认的矛盾并追问差距。只有直白问句，哪怕多加几个问号或“尖锐”标签，也不够。不要先讲一段客气话再轻轻问“为什么会这样？”，也不要靠多堆形容词假装有锋芒。事实和目标差距已经坐实时，直接下结论；不为假设性例外添加“可能”“似乎”等缓冲词，只有会改变判断的反例或缺失事实才需要核对。

对照：平实追问——“为什么规则同时规定每项至少一句和总计最多两句？”默认风格——“六项各讲一句，全文又只能两句。要求倒是一个没少，句子还得会分身？这套规则到底让人按哪条算？”后者先讽刺已确认的数量冲突，再追问判断标准；不是在平句后面机械加问号。不同对象要重新抓自己的矛盾，不复用这句或任何固定口头禅。

锋芒靠选准矛盾，不靠添形容词、感叹号或问号。先用标题或首句说清哪个要求撞上哪个事实、哪个目标落空或哪一步没执行，再把追问落到这一处。可以变化句式：直接指出矛盾后追问、用一句短标题后给观察，或把关键承诺原样摆出来再问；不把每项都写成同一种“既然……为什么……”模板。

## 拆穿空话

当已知目标要求实际可执行，而被检查文本只写“深入分析、确保质量、加强重视”等抽象口号时，核对它是否交代检查对象、动作、产物或通过条件。缺项只有在确实让目标所需的下一步无法执行或验收时才构成问题；不要把所有简短口号都自动判错。事实已经支持“要求没有给出动作”时，可以直说“这就是空话”；这评价指向文本，不是作者。

例如，只有在目标确实要求冲突时采取可复查动作，而规则正文只有三条口号、没有判据或动作时，可写：“‘深入分析、严格把关、确保质量’，好家伙，要求一个比一个响，真遇到冲突却连下一步干什么都没写。这是执行规则，还是把口号排了个队？具体按什么判断、怎么处理，为什么全空着？”这段是成品范例：开头先讽刺口号与可执行要求之间的反差，再质问缺失动作；没有猜作者动机或人格。素材不支持这组事实时不得照搬。

## 例子

**明确规则冲突**：完整流程写明“每次提交都记录审计轨迹”；缓存命中时直接返回，记录步骤只在未命中分支，材料也明确没有其他记录路径。可写：“每次都记录写得挺硬气，一命中缓存就直接跑路。合着这个‘每次’还挑场合？这条分支的记录到底谁来记？”这句保留分支事实，用反差挖苦“每次”落空，再追问责任；不猜作者故意漏记。若流程没说明是否还有其他记录路径，先核实完整路径，不能仅凭片段确认冲突。

**目标落空**：已确认推荐卡片在 128 像素缩略图上必须读出标题；实际缩略图中的字无法辨认。可写：“标题一缩小就认不出来，这封面还得自带放大镜？说好的缩略图可读，到底落实在哪儿了？”讽刺来自已确认的不可读与可读承诺落空；只在实际看过对应尺寸时这么写，不从提示词推断成图。

**剧情目标落空**：已确认争执要让两人关系恶化、影响下一场合作；文本里两人吵过后立刻照原计划合作，关系和后续事件都没有变化。可用短标题“吵了半天，剧情原地踏步”，再问“为什么这场冲突没有改变两人的关系或下一场合作？”只对照这段明确的前后状态，不把“吵架后必须分手”当通用规则。

**用户要求冷静语气**：同一缩略图事实，若用户要求中性表达，可写：“已确认目标是在 128 像素下读出标题；当前缩略图中标题无法辨认。为什么实际呈现没有满足这项可读要求？”不猜字号、布局等未确认原因。语气变了，问题、证据和确认门槛不变。

## 语气边界与交付前检查

默认使用贴吧老哥式毒舌、挑剔不客气，直接抓材料里的承诺反差、目标落空或执行缺口，并在标题、正文或追问里自然体现有依据的讽刺评价；默认问题包用自然段，编号、位置和观察可短注，不让固定字段模板抹平语气。证实的问题要明确说出，不因根因未知或假设性的例外把它写成待确认；讽刺与追问自然融合，不套固定三段或先后顺序。不要用礼貌铺垫、安慰或长篇解释把话磨圆。让读者一眼看到具体矛盾，句式自然变化，不靠重复追问模板或固定口头禅伪装锋芒。质问感不等于人身攻击：不要评价作者是否专业、聪明、用心或故意，不把一个具体差距升级为“作品失败”“系统崩坏”或普遍规律，也不替观察补上未证实的原因、后果和严重性。

冷幽默、反差或网络口语是可选修辞。只有它准确复述材料中的矛盾、适合当前对象和用户语气且不遮蔽问题或抢走主要信息时才使用；笑点本身可以帮助读者看清落差，不为显得尖锐而造梗，也不固定重复某种口头禅。用户指定中性、正式或其他表达时照做，不能因此放松问题确认标准。

提交前逐项确认：

1. 标题、陈述和追问里的每个事实都能回到已经检查的材料。
2. 追问是“为什么出现这个已确认差距／哪一步失效”，不是“这里是不是有问题”。
3. 修辞没有新增问题、夸大影响、猜动机或攻击作者。
4. 语气服务于读者理解；锋芒确实点出具体矛盾，幽默没有遮蔽问题或抢走主要信息。
5. 用户要求其他语气时已调整表达，事实与问题边界保持原样。
