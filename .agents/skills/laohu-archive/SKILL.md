# 作品收录与目录管理

为每件作品守住唯一、安全、不串台的存放位置，办完立刻把路径交回原创作流程。**不重做需求访谈，不代替创作，不越权写盘。**

## 1. 准入门禁与仓内外验身

1. **无保存授权绝不进入**：遵守 `docs/runtime.md` §2，仅在用户明确要求建目录、保存/归档/收录文件、准备参考库容器，或当前任务已有明确保存授权时启动。单纯讨论、起名、定方向或换媒介继续在聊天交付；项目规则、通用知识与 Skill 代码不作为作品收录。
2. **承接已有结论，不重问创作意图**：直接从上下文沿用已确认的作品名、独立归属、既有 `{WORK_DIR}` 与调用负责人；不因调用归档把单次保存扩成保存全部草稿，也不把既有目录自动当成新一轮写入授权。
3. **真假老胡仓硬验身**：判断当前是否在老胡项目内，**只看宿主工作区 / 当前任务目录解析后的物理路径及其 Git 顶层是否就是 `{PROJECT_ROOT}`**。Skill 从全局软链加载、客户仓库恰好也有同名 `AGENTS.md` 或 `works/`、或临时切换终端目录，**均不代表任务在老胡仓内**。

## 2. 8 种情境分诊与命令执行

按当前现状对号执行；所有脚本优先**不带 `--write` 预览**，核对路径与权限无误后再落盘。无法运行脚本时，读同一 `categories.json` 用文件工具做同等路径、符号链接、大小写与 Unicode 重名检查后再操作，位置或归属不明即停。

| 情境 | 先核对什么 | 动作与精确命令（[workspace.py](scripts/workspace.py)） | 停止与告知 |
|---|---|---|---|
| **① 老胡仓内新建** | 从 [categories.json](references/categories.json) 选固定英文分类；核对名称无非法字符 | `python3 "{SKILL_DIR}/scripts/workspace.py" --category <分类> --name "<作品名>"` → 预览无误且获授权后加 `--write` | 仅建必要目录，不建空子目录或空稿；聊天明说“已创建作品目录：`<路径>`” |
| **② 老胡仓内同作品复用** | 核实该目录确属同一作品（含跨媒介，如歌的封面沿用 `works/music/<歌名>/`） | 预览并确认后加 `--reuse --write`（同目录绝不因换 Skill 另建新类） | 聊天明说“继续使用作品目录：`<路径>`”，绝不说成“新建” |
| **③ 用户已给精确路径**（项目外或仓内另指定） | 路径为绝对路径、无 `..`/符号链接；如已有内容须先确认是否同一作品 | `python3 "{SKILL_DIR}/scripts/workspace.py" --work-dir "<精确路径>" --location-confirmed` → 预览无误后加 `--write`（复用再加 `--reuse`） | 不追加 `works/`、分类或作品名；用户给的是父目录时结合作品名确认最终路径 |
| **④ 项目外/环境不明且位置未定** | 当前项目路径与组织规则是否真实可靠（不虚构不存在路径） | **严禁建目录或默认回退老胡仓**；提出 1–2 个有依据的实际建议路径（如当前项目合理路径与/或老胡仓对应路径）请用户拍板 | 状态返回 `待确认位置`，确认前不传 `--location-confirmed`、不写盘 |
| **⑤ 缺少作品名称** | 查上游是否已有确认名或用户认可的工作名（无需等最终传播标题） | 不自造“未命名作品”，不从归档循环调用标题/灵感 Skill | 状态返回 `待命名` 并交回原创作负责人讨论命名 |
| **⑥ 新作品名称被占用** | 核查同名（含大小写/Unicode 等价名）已有目录是否属另一作品 | 不静默合并、不覆盖、不自动加日期或 `_2` 序号 | 告知冲突路径并提可用新名由用户选择 |
| **⑦ 多个候选归属不明** | 检查已有路径、来源文件与相关分类，不单凭同名或当前媒介硬猜 | 列出各候选实际路径与内容区别，有依据时推荐一处并说明理由 | 状态返回 `待确认归属`，就地澄清，确认前不用 `--reuse` 或复制移动 |
| **⑧ 长期参考库容器** | 区分独立分析作品（`works/benchmark/<作品名>/`）与长期参考库容器 | 见下方 [参考作品库容器](#参考作品库容器) | 建容器不等于批准本轮写入分析数据 |

> **分类与命名三条硬规矩**
> - **一作一目录，按最终独立作品归属定类**：`music` 共用歌词与编曲，歌曲的配套封面/音频/视频仍留原 `music` 目录；独立封面才入 `cover`；灵感、选题、标题、对标附属于已有作品时跟随原目录，独立成果集合才用各自分类；诊断附着原作品，进化入规则/知识库，更新不产作品类。不自动新增一级分类。
> - **作品名 ≠ 封面大字 / 传播标题 / 文件名**：封面字或发布标题改动时，不自动给已有目录改名。
> - **非法名不静默篡改**：名称禁用路径分隔符、控制字符、`.` 开头、尾随点、`..` 及系统保留名；不合规时给可用建议并确认。同一作品已确认的位置在后续换 Skill/换媒介/恢复任务时持续有效，不重问；用户改指新位置时更新交接，不自动搬迁旧文件，也不把单次选择写成跨项目永久偏好。

## 参考作品库容器

长期参考库独立于 `works/` 分类，由 [library-layouts.json](references/library-layouts.json) 管理。**新收录的跨项目专业研究默认归接收 Skill 同级 `benchmark/`**，路径规则见 [laohu-benchmark](../laohu-benchmark/SKILL.md#选择研究库)。

仅当用户明确要求准备兼容项目根库或其他指定参考库容器时，使用 [library_workspace.py](scripts/library_workspace.py)：

```bash
# 项目根兼容容器（先预览，授权后再加 --write，确认复用加 --reuse）
python3 "{SKILL_DIR}/scripts/library_workspace.py" --library benchmark --root "<已核验项目根>"
# 外部已确认容器（位置先经用户确认，再传 --location-confirmed）
python3 "{SKILL_DIR}/scripts/library_workspace.py" --library-root "<已确认绝对路径>" --location-confirmed
```

返回的 `work_dir` 即传给 benchmark 工具的 `--library-root`；准备容器不代表授权本轮写入研究记录。

## 3. 后续文件组织与外部文件收录

- **目录内保持轻量**：小作品文件直接放 `{WORK_DIR}`（如 `lyrics.md`、`arrangement.md`），确有多套独立方案或工具要求再按真实差异命名或分子目录（如 `arrangement-acoustic.md` / `arrangement-electronic.md`）。同方案修订更新原主稿，覆盖重要已有内容前留恢复依据，不造 `_最终版` 平行主稿，绝不覆盖已有用户文件或原始素材。
- **外部文件收录先交干跑清单**：用户要求把外部零散文件收进作品目录时，落盘前先核对并列出**来源路径 → 目标路径 → 重名处理**；**默认复制保留源文件**，仅收录实际需要的文件。明确要求移动文件或目录改名时，先检查依赖与引用、说明受影响路径再按授权执行，不扩成整盘搬迁或公共知识库收录。

## 4. 聊天告知与交回创作负责人

- **面向用户（必须告知、说清状态）**：遵守 `docs/runtime.md` §2，每次实际创建、复用或收录文件后，当轮聊天必须用直白的话给出实际绝对路径（支持链接时可点击），严守“**已创建作品目录**”与“**继续使用作品目录**”区分，并列出本次实际收录/写入的文件；不宣称外部目录天然被 Git 忽略，也不擅自修改外部 `.gitignore` 或提交文件。
- **交回调用负责人（内部交接，不向用户硬贴僵硬表单）**：把 5 项事实（作品名称、分类/外部定位、实际绝对路径、状态 `新建 / 复用 / 待命名 / 待确认位置 / 待确认归属 / 失败`、原负责人下一步）交回上游，立即退出归档角色、不占据创作主导权。
