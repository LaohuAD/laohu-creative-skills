# 四层能力进化与回归

这份 Reference 用于创建第三层 Skill、重构已有能力或迁移成熟项目机制。简单的文字修正、单次作品修改和确定性格式转换不必读取。

## 能力先于文件

先画出能力关系，再决定文件位置。一个 Skill 可以同时承担四层作用；一个 Reference 也可能服务多个作用。文件数量、目录层级和标题数量不能证明能力完整。

每条准备写回的能力至少回答：

```text
触发：什么请求或失败会进入？
判断：这次真正要保住什么，冲突时放弃什么？
动作：Agent 要做什么选择或操作？
原因：为什么这个动作能改变结果？
条件：在哪些材料、载体、用户和约束下成立？
例外：什么时候不能照做？
结果：怎样从中间产物、成品或使用反馈看出它生效？
```

如果只能写出愿望，不能写出动作和结果，先保留为待验证经验，不要升级成硬规则。

## 四层的编译方式

| 内部作用 | 编译成领域能力时要回答 | 常见误区 |
| --- | --- | --- |
| 灵魂 | 任务为谁改变什么；主要冲突和主胜负手是什么；愿意牺牲什么 | 用漂亮箴言代替取舍；把一次题材偏好写成全局原则 |
| 筋骨 | 入口、状态、顺序、交接、推进和回收怎样成立；谁拥有裁决权 | 把步骤罗列当作结构；让多个 Skill 重复收集同一状态 |
| 血肉 | 哪些材料足以承重；哪种领域技法在当前位置改变什么效果 | 只列名词和技巧；用技巧掩盖材料不足或事实错误 |
| 表皮 | 哪些规格必须精确；哪些分寸要在真实媒介和关系中校准 | 用禁词、计数和模板证明自然；用审美解释绕过硬规格 |

编译时保留领域原生名称。下游可以完全不出现“四层”四个标题，只要它的职责真实承接了四种作用。

## 迁移与去向

对每条旧能力做一次去向判断：

- **保留：** 负责人、触发和结果都仍然正确，记录保护项。
- **迁移：** 机制有效但路径或语言属于旧项目，先还原作用，再写成新项目的领域规则。
- **合并：** 多条规则解决同一个判断，合并后保留条件、例外和来源，不只保留一个标题。
- **重写：** 目的成立但旧动作失效，保住目的，替换动作并留下回归任务。
- **退役：** 已重复、冲突、长期未使用或被证据推翻，记录原因和恢复位置。
- **待观察：** 有独特价值但证据不足，放入经验记录，不作为强制门槛。

迁移不是复制文件。必须检查旧规则是否真的被新入口调用、是否仍有必要输入、是否影响相邻好任务，以及旧项目中的更成熟机制是否被新蓝本降级。

“老胡的审美起源”提供的是进化方法的成熟来源，不是造梦技能的运行时父目录。迁移时只带入能改变判断、调用或验证的机制；来源项目自己的领域 Skill、私有素材、路径和历史台账继续留在来源项目中。新项目必须能在自己的 skills/、works/、knowledge/ 和真实请求中独立运行。

## 回归矩阵

至少准备四类任务，按目标项目实际领域改写：

1. **代表任务：** 原规则本来应该解决的常见任务。
2. **相邻好任务：** 同一能力但不同材料、载体或受众的合理任务。
3. **反例任务：** 表面相似、实际不该触发同一规则的任务。
4. **失败复现：** 能稳定重现原问题的任务，用于确认最早断点真的被修复。

对照记录改前、改后和必要时的简化基线。结构和路由可用机械检查；行为要看实际决定和产物；质量要接触最终媒介或真实接收者。没有运行的环节写 `UNKNOWN`，同一修改者的自评最高写 `OBSERVE`。

## 重新唤醒与恢复

出现以下情况时，重新读取本 Reference 并开启一轮进化：

- 新 Skill 只有“持续进化”口号，没有负责人、台账、回归任务和回退位置；
- 多次反馈都被写成禁词，却没有回到最早取舍或流程断点；
- 下游目录出现四层标题，但领域原生能力仍不可执行；
- 新项目复制了通用蓝本，却丢掉成熟项目已经验证的机制；
- 验收只检查文件存在、命令可运行或静态分数，没有真实行为和质量证据。

每次长期改动都应能回答“如果这次改错，怎样恢复到改前状态”。Git 提交、迁移记录和代表任务输出共同构成恢复依据；不能只保留最终文件而丢失改前证据。
