# 老胡造梦技能自我进化

这个 Skill 负责让造梦技能随着真实创作继续生长。它处理的是长期能力建设：创建一个新的第三层 Skill、修复已经失效的 Skill、把领域方法落成 Reference，或把成熟项目里已经验证过的进化机制迁移进来。

用户只要当前作品、当前答案或一次性改稿时，不进入长期进化；先完成当前任务。只有用户明确要求创建、升级、沉淀、迁移、重构或更新项目能力时，才修改 Skill、Reference、顶层规则或长期资产。

## 四层能力的定义

四层是检查能力是否从判断走到结果的内部坐标，不是下游 Skill 必须照抄的四个标题，也不自动对应四个文件。

- **灵魂：取舍与方向。** 说明这项能力替谁改变什么，什么冲突决定结果，冲突时宁可放弃什么也要保住什么。它可以是作品的命题、情绪关系、观看体验或任务目标，不要求每项能力都写成一句箴言。
- **筋骨：整体与承接。** 说明任务从哪里进入，状态怎样传递，各部分为什么有这个位置，怎样推进、转折和收束，哪个能力拥有判断权。它可以表现为创作流程、状态机、调用关系或交付结构，不能退化成步骤清单。
- **血肉：材料与技法。** 说明哪些事实、案例、人物、声音、画面、资产或领域知识有资格进入，以及用什么专业方法让材料产生本次需要的效果。只列技法名称、不说明它改变了什么，不算血肉。
- **表皮：法度与分寸。** 说明路径、字段、尺寸、格式、权限等硬规格怎样验收，以及语言、节奏、视觉和媒介分寸怎样通过实际接收来校准。硬门不能靠审美解释抵消，软性分寸也不能伪装成禁词和计数。

上层失准时，不靠下层堆技巧补救；下层缺位时，上层也不能停在道理里。四层之间允许往返：试作暴露的问题可以回到方向，表皮反复失败也可能说明筋骨或血肉选错了。

## 先判断要改什么

收到进化请求后，先给出结论：本次应该创建第三层 Skill、补一个 Reference、修改现有负责人，还是只改当前作品。再说明依据。按以下顺序判断：

1. **确认真实目的。** 用户是在解决一个当前结果，还是要让以后同类任务持续变好？不要把“这次改得更好”自动升级成项目规则。
2. **定位最早失效点。** 先查目标、取舍和接收者，再查整体承接、材料技法和呈现规格。不要因为最后看到一句话难看，就直接追加语言禁令。
3. **确认负责人。** 已有 Skill 能承担，就修改它；只有触发条件、交付物和判断过程确实独立且反复出现，才新增 Skill。方法性知识放 Reference，确定性转换才写脚本。
4. **保护已有能力。** 读取当前文件、未提交改动、被忽略的用户资产和真实作品；不只以 Git 的 HEAD 作为完整基线。删除、合并或迁移前，确认有效条件、例外和可恢复位置没有丢失。

## 创建或升级第三层 Skill

造梦项目的可调用 Skill 采用扁平发现：需要被 Agent 独立检索的能力，放在 `skills/` 下的独立目录中，用连字符表达层级，例如 `skills/laohu-lyrics-rhyme/SKILL.md`。不要依赖嵌套目录自动注入上下文。

创建或升级时，按真实领域语言编译四层作用：

- 先写清触发条件、目标用户、输入、输出和停止条件；让 Agent 能在一次请求中判断是否该进入。
- 把灵魂翻译成该领域的职责和核心取舍，把筋骨翻译成该领域的流程、状态和交接，把血肉翻译成专业材料、方法和示例，把表皮翻译成格式、媒介、权限和质量门。
- 不要求下游出现“灵魂、筋骨、血肉、表皮”四个词。歌词 Skill 应该写曲式、可唱性、段落关系和韵脚；封面 Skill 应该写主体、构图、景别、光影和提示词；这些领域原生职责才是继承是否成功的证据。
- 需要独立调用的能力放成同级 Skill；只在上游流程中按条件读取、不能独立完成任务的方法，放在对应 Skill 的 `references/`。
- 每个重要规则都要包含触发、动作、原因、成立条件、例外和可观察结果。只有口号、愿景或四个空标题，不算能力落地。

## 进化工作模式

按请求选择一种模式，不把所有模式混成一份报告：

### 创建（CREATE）

从真实重复需求、已解决的问题或成熟项目能力出发，生成一个可独立调用的 Skill 或 Reference。先验证它是否已有负责人，再写最小可用入口；把必要的领域方法、案例和边界放到正确位置。

### 修复与升级（REVISE）

保存改前基线，列出失败事实和最早断点，只改能解释该断点的负责人。改完后检查原有好任务、相邻任务和反例，避免把一次反馈扩散成所有任务的永久禁令。

### 迁移（MIGRATE）

从成熟项目读取原始规则、实际交付和验证记录，先还原它真正改变了哪些选择，再编译到造梦项目的领域语言。有效机制迁移，旧项目专属路径、无证据启发式和重复规则不照搬。迁移必须留下来源、去向、保留理由和回归范围。

从“老胡的审美起源”（本地项目目录可能仍称为“老胡的审美 Lora”）迁移时，把它当作方法来源而不是可整包复制的上级项目：分别检查它的顶层规则、进化 Skill、Reference、台账、脚本和行为场景，优先吸收已经通过真实项目验证的机制，再按造梦技能的入口、权限和资产边界重新编译。

### 经验落地（CAPTURE）

把真实创作中的反馈、失败、人工删改和结果差异整理成待验证经验、项目规则或长期资产。证据不足时保持待观察，不因为写进文件就宣称模型已经“学会”。

## 验证与交付

完成修改后，分别检查四类证据：

- **STRUCTURE：** 文件命名、frontmatter、Reference 链接、目录和格式是否正确。
- **ROUTE：** 从真实请求能否找到这个 Skill，并能走到正确的 Reference 或输出；静态检查最多说明 `OBSERVE`。
- **BEHAVIOR：** 代表性请求是否真的改变了判断、流程、中间结果或成品。
- **QUALITY：** 最终接收者、实际媒介、领域专家或真实结果是否证明质量提高；缺少这些证据时保持 `UNKNOWN`。

底线门和巅峰门分开：底线门阻止事实、权限、接口和格式错误；巅峰门判断本次最值得赢的取舍是否得到最强支持。通过底线不能等同于值得交付，同一执行者的试写和自评不能冒充独立验证。

交付时说明：改了什么、为什么改、来源和去向、验证覆盖了什么、哪些效果仍未证实、如何恢复。更新工具箱方法不能覆盖 `works/` 中的作品，也不能覆盖 `knowledge/` 中的个人事实、案例和已确认偏好。密钥、本机配置和无追溯价值的临时文件不得进入仓库。

复杂重构或成熟项目迁移时，读取 [四层能力进化与回归](references/four-layer-evolution.md)。普通的小范围 Skill 修改不必加载整份 Reference。
